# Project Memory

This file is intentionally short. It records only cross-cutting decisions that are easy to violate and should be loaded for every task. Use the [documentation index](README.md) to open detailed references only when the task needs them.

## Platform Invariants

- [Editor undo](EDITOR_UNDO.md): restore saved code as a baseline, never as a full-document undoable edit. Keep undo/redo only in mounted-session memory, isolated by Test attempt/view, question, and file; dispose it on departure/account/attempt changes. Reload/reopen starts from the saved answer with empty history. Loading cannot autosave blank/starter text; normal edits and undo/redo must keep using ordered answer autosaves.

- [Activity content access](ACTIVITY_CONTENT_ACCESS.md): optional General-only closure blocks student prompts, answers, histories, solutions, reports, and exam files once effective attempts/dates end. Keep valid started/reopened attempts usable, staff records intact, and only receipts/released totals visible after closure. Enforce through the shared assigned-route guard, grade projections, and media access; finalization may finish expired saved work but cannot return protected content.

- Public release notes contain only Highlights, Fixed, Database migrations (Yes/No and commands), and Environment variables only when changed. Keep bullets short and omit approvals, names/dates, rehearsal reports, and deployment narratives.
- Public deployment docs and release notes contain generic examples only. Actual infrastructure inventory and per-environment evidence belong in private operator notes outside Git; an optional local .git/info/cognelo-operations pointer locates them.

- [Application time](APPLICATION_TIME.md): administrators choose the default timezone and may enable course overrides (off by default). Courses inherit until an explicit owner/admin chooses a zone; disabling overrides uses the application zone without deleting choices. The course layout supplies the effective zone to all nested pages/plugins. Persist UTC instants; never use browser timezone defaults. Availability and deadlines remain server-clock decisions. Client availability displays use a server-synchronized monotonic clock; open date forms retain their loaded timezone until reload.

- [Student solutions](ACTIVITY_SOLUTIONS.md) are opt-in per course activity, shared by sections, with one switch for a whole Test. Summative solution access additionally requires grade release. The learner must explicitly reveal the solution; private reference source is projected by the owning plugin, never added to ordinary coding/Web Design config or grading reports. Grade feeds must not expose provisional results for repeatable summative assignments.

- [Live activity authoring](LIVE_ACTIVITY_AUTHORING.md): course questions and private tests remain editable during attempts with an active-student warning, optional message, and atomic audit. Learner responses survive refresh; submitted Tests use their final revision. Summative result/history APIs must enforce grade release, and missing automatic tests produce submitted-ungraded work rather than fabricated scores.

- Teacher course workspaces have one thin subject/course identity header above the tabs; panel headings do not repeat that identity. Other working pages reuse existing headings/controls rather than large decorative heroes. Retain semantic page titles and mobile wrapping. See [Frontend platform decisions](reference/PLATFORM_DECISIONS.md#frontend-platform-decisions).
- Course-content mutation refreshes must keep the existing tree mounted. Replacing it with a loading message collapses the page height and loses scroll position; reserve that loading state for initial loads and workspace navigation. See [Course content tree](COURSE_CONTENT_TREE_IMPLEMENTATION_PLAN.md#phase-7-unified-teacher-content-tree---complete).
- Synthetic email recipients, including `cognelo.local`, are captured in the private local outbox at the shared delivery boundary, even when real SMTP/Graph is configured. Keep system-mail eligibility checks before capture; never fall back to a provider when capture fails. See [Email delivery](EMAIL_DELIVERY.md).
- Keep `apps/api` and `apps/web` separate. Shared business rules belong in `packages/core`; shared schemas belong in `packages/contracts`.
- Keep core persistence generic. Activity- or content-type-specific tables, migrations, routes, services, translations, and UI belong to the owning plugin.
- Treat browser-visible activity config as public student data. Hidden tests, private reference solutions, raw model output, private prompts, credentials, and grading internals stay server-side in authorized storage and routes. Explicit solution release exposes only the intended reference content through its gated provider.
- Plugin dispatch is explicit and fail-closed. A route must declare supported type keys, and authorization must be checked for its course, bank, group, or content-resource context.
- Bank activities are reusable authoring sources; course activities are independent copies. Changed Published saves create immutable generic versions. Bank-to-course retrieval is blocked after any attempt, while course-to-bank publication may create a new bank version without modifying attempted course content.
- Reusable bank Tests own independent hidden bank-activity children and publish an immutable composition manifest that points to exact child versions. Importing or publishing a Test deep-copies the whole graph and delegates every child's private data to existing plugin lifecycle hooks. Test provenance is already retained for compound synchronization, but generic single-activity sync must reject Test shells until graph-aware synchronization is implemented.
- Bank variations are background jobs built on the ordinary deep-duplication lifecycle. The host preserves the source concept selections and asks the owning plugin to regenerate a genuinely different draft at comparable complexity; reusable Test variations do this for every child and fail before copying if any child lacks the explicit variation capability. Completion reports the final stored activity title and any plugin-returned review warnings, grouped by affected copy. Recoverable Programming Exercise test-generation failures keep validated subsets or test-free drafts; other Test children continue. Thrown generation failures compensate by deleting the whole copied graph, retries plugin-private cleanup hooks up to three times, and explicitly reports any cleanup that remains incomplete.
- Plugins with private bank-owned data must implement every relevant copy, synchronization, duplication, deletion, activation, backup, and restoration hook. Moving a bank activity keeps its ID and normally requires no copy.
- Core owns attempts, attempt limits, gradebook lifecycle, release visibility, audited regrades, research events, and mechanism-neutral grade challenges. Course assignment policy distinguishes `formative`, `formative_ai`, and `summative`, but every standalone submission/check still writes a stable core attempt whose mode is only `formative` or `summative`; both formative policies create formative attempts, and only the explicit `formative_ai` policy may invoke and expose automatic learner AI feedback. Only summative attempts can contribute to grades or consume summative limits. A confirmed change from summative to either formative policy deliberately converts its existing attempts to formative, deactivates current grades, hides release, and records per-participant audit events; either formative policy changing to summative preserves old formative attempts and only future attempts are summative. Grade challenges are disabled by default on each summative course activity and use the ordinary General/section/team/student assignment policy. When enabled for the learner's assignment, its released final grade is challengeable regardless of source and separately identified generated or teacher-authored feedback may expose another target; disabling the setting blocks only new challenges and preserves existing records. Submitting a challenge automatically emails every active course-wide grading teacher and active teacher assigned to that section through guarded system mail; TAs and unrelated administrators are not notification recipients, and delivery failure never rolls back the saved academic record. Challenge queues must enter grading through the same plugin **Review and grade** surface as the gradebook; the challenge panel only sends the response and may notify the student by guarded system email. Plugins own activity-specific evaluation and sanitized feedback contracts. A plugin-specific released learner report must independently recheck learner ownership and release state and expose only bounded student-safe evidence.
- [Reopening the last submission](SUBMISSION_CONTINUATION.md) returns the same attempt to started with saved answers and the original start, applying current General/section/team/student settings (including later extensions). It never grants a new attempt or resets time. Restore plugin state and withdraw/recompute the grade atomically; preserve prior completion and grading evidence in `submission_reopened` events, which invalidate older score candidates for that attempt.
- [Submission deletion](GRADEBOOK_IMPLEMENTATION_PLAN.md#submission-deletion) is a shared gradebook row action, independent of plugin review renderers. Require a teacher-provided nonblank reason, reject unfinished attempts, retain the attempt and audit history, and keep the deleted record/reason visible to its student. Never expose raw grade snapshots in learner deletion history. Render retained submitted code/files, not reference solutions. Supported submission-history tabs must be usable before a timed start, without initializing drafts or creating attempts.
- Grade release is fail-closed for submitted work: submitted-ungraded learners and plugin-declared partial component grades block release, while learners with no submission do not. Plugins with multi-component grades must implement the batch completion contract; an explicit teacher final-grade override is complete.
- Detailed gradebook actions are capability-driven and use one cross-activity vocabulary: **Class overview** for aggregate reporting, **Rerun automatic grading** only where a current-answer grading handler exists, **Assess with AI** with an explicit grade-impact warning, and **Review and grade** for the teacher's answer, feedback, rubric, and final-grade work. Per-student actions live in the shared three-dot contextual menu so adding capabilities does not widen every result row. Do not show disabled “Unavailable” grading actions.
- Course workspace tabs must not share one blocking data barrier. Content renders only after its own content-tree requests settle and never shows an empty-state message while loading. Course folders default to collapsed; per-user/course/section/view expansion persists locally for four hours, renewed by returning to Content or a folder action. See the [content tree plan](COURSE_CONTENT_TREE_IMPLEMENTATION_PLAN.md). For staff who can view grades, opening an activity from the course content tree enters the shared activity-report workspace rather than authoring: **Class overview** is the default tab, **Student results** reuses the detailed gradebook rows, and an always-visible permission-gated action links to the existing editor. Section activity links and legacy assigned URLs enter the same Class overview / Student results workspace for course managers, scoped to the section. Its compact secondary actions include Edit activity and the same activity-settings modal used by course content, gated by course-management capability. Edit opens the shared Activity / Concepts / Grading authoring shell; learners remain on the assigned route. The Gradebook tab loads a compact server-computed aggregate only when active; participant rows and attempt histories remain confined to detailed gradebook views and exports. While **Student results** is visible, the page polls a lightweight authorization-scoped feed—not the full gradebook—to show each current-mode attempt in progress with its attempt number and start time. Individual review dialogs load the newest current-mode submission first and retrieve older attempt payloads only as the teacher navigates; historical and formative attempts are read-only for grading. Gradebook activities follow the canonical depth-first course-content order rather than alphabetical order; a shared placement wins over assignment-backed duplicates, group-only placements use their earliest relevant position, and unplaced activities follow with a deterministic fallback. Per-activity CSV/XLSX grade exports use plugin completion status and contain only complete normalized final grades; partial, ungraded, formative, and non-submission rows are omitted. Deleting a content folder is an all-or-nothing batch deletion of its contained activities: any recorded core attempt, including soft-deleted history, blocks the whole folder and the UI names every blocker. An activity with attempts can be deleted only through its activity deletion flow after a dedicated data-loss warning followed by the ordinary confirmation; deleting a placement alone is rejected.
- Course activity assignment settings use General → section → teacher-prioritized team → student precedence, independently per overridden field. Team membership is resolved dynamically, including hidden groupings; student exceptions always win. See [Activity assignment exceptions](ACTIVITY_ASSIGNMENT_EXCEPTIONS.md). Any formative or summative activity may have a General time limit; a group can inherit, replace, or explicitly disable it. Starting a timed standalone activity creates a core attempt; unsubmitted work resolves policy live, with deadlines recalculated from the original start, capped by the effective Until date after exception resolution, and refreshed within 20 seconds. Countdown, write guards, and timeout finalization share that deadline; submission snapshots both the effective duration and Until date. Settings saves warn when students are answering and can atomically broadcast an optional in-app notice; submitted timing stays fixed. The host blocks pre-start writes, shows the server-derived countdown, requests the plugin's ordinary final submission at zero, and preserves an ungraded timed-out attempt when a plugin cannot complete. A Test's authored limit is only a creation/import default copied into this independent course policy; later Test-authoring edits do not alter the course setting. Materialized `CourseGroupActivity` rows are the authoritative assignment state: activities with no assignment rows show every group unchecked, and groups created later never inherit existing activities automatically. Every assignment must also retain a matching assignment-backed `CourseContentItem`; core creates a visible root placement when no destination was supplied, the database materializes one for low-level inserts, and deferred integrity triggers reject removing the last valid placement while the assignment survives.
- Live activity messaging is core-owned and attempt-scoped. It defaults off and is enabled in the activity’s General course-content settings, shared by all sections. Learner polling and answering presence continue while disabled so enabling takes effect during an attempt and live-settings warnings remain reliable; stored history and broadcasts are gated by the switch. See [Activity messaging](ACTIVITY_MESSAGING.md). A teacher can broadcast from the activity report only to learner conversations seen within the recent-presence window; explicit course teachers/admins can reach all assigned groups, section teachers only their sections, and TAs cannot broadcast. Messages, generic sender identity, and per-user read state are persisted per participant and attempt. A new attempt receives a distinct empty conversation and cannot see a prior attempt's messages. Timed activities and compound Tests require a started core attempt; untimed standalone activities use the learner's next logical attempt without creating an academic attempt merely by opening the page. Opening/renewing presence remains assignment-, visibility-, availability-, and SEB-gated; learners retain ownership-checked access to stored notices when live settings close access. The shared live-control container presents the timer and unread/blinking message control as one bubble; when the timer is present, only the envelope is shown behind a rounded timer separator while retaining its accessible label. Persistence already supports student/system senders for a later bidirectional policy, but the current API permits staff broadcasts only.
- Summative model evaluation is teacher-triggered unless a feature explicitly documents another policy. Formative feedback may run from the learner's explicit check or submit action. Learner copy must not reveal the grading mechanism.
- Every direct plugin that advertises AI grading must implement the shared guided-batch contract: expose current instructions, persist edited instructions on request, and validate complete grading content on submitted/graded examples. Core caps examples at three, revalidates same-activity ownership/completeness, excludes examples from batch targets, and never sends learner identity to the model. Per-run instructions apply even when the teacher opts not to update activity settings.
- Research and audit records are append-oriented. Preserve immutable request/configuration snapshots, provenance, event history, and release visibility; do not silently rewrite historical evidence.
- Shared authoring forms use the common unsaved-change guard and `EditActionBar`. Activity knowledge selection is host-owned, includes exact skills and misconceptions, and shares the activity draft/save boundary. Legacy concept misconception `NULL` is empty; graph saves persist explicit arrays.
- [Test timeout recovery](TEST_COMPOUND_ACTIVITY_IMPLEMENTATION_PLAN.md#timeout-recovery) runs on authorized teacher results/gradebook reads, never a scheduled worker. Resolve live exceptions before recovery; preserve saved responses as submitted-ungraded work at the effective deadline and audit recovery separately. Countdowns use server remaining time plus monotonic elapsed time, and deferred/failed browser submissions back off for 20 seconds. Recovery and queued autosaves must serialize on the parent attempt.
- [Test automatic regrading](TEST_COMPOUND_ACTIVITY_IMPLEMENTATION_PLAN.md#teacher-automatic-regrading) reruns every manifest child using current grading rules, with progress for individual and whole-class actions. Preserve original responses/timing, audit child changes, and leave the parent total unchanged after any pending/failed child. AI/manual child grading uses aggregate-only recomputation.
- Compound Test manual submission is last exercise → answer review → final grading confirmation. Review status is plugin-owned response presence, never correctness; keep the parent attempt mounted so timing, autosaves, messaging, and no-resume session identity survive review navigation. Deadline expiry still submits automatically. See [Compound Tests](TEST_COMPOUND_ACTIVITY_IMPLEMENTATION_PLAN.md).
- Reuse the shared editor, Markdown, rich-text, media, dialog, notification, and icon layers instead of creating plugin-local alternatives for platform behavior. Cognelo-owned confirmations and text prompts go through `DialogProvider`; native browser modal APIs are reserved for learner-authored code inside explicitly sandboxed previews.
- Student view is a forced learner projection for an authenticated teacher, never impersonation. It shares the real learner course-content component (including layouts and material links) while substituting preview activity URLs and omitting individual grades/submission state. Every activity definition explicitly declares interactive, read-only, or unsupported behavior; dedicated client/server registries validate the declaration and fail closed, while the browser API blocks ordinary mutations from preview pages. The SDKs are plugin-independent contracts/registries; the outer `plugin-registry` composition root registers installed plugins by stable key, production startup and plugin-registry integration tests validate the complete graph, and development avoids validating transient hot-reload graphs. Core, DB, SDK, shared UI/contracts/config, and sibling plugins must never import concrete plugins; `npm run architecture:check` enforces this before tests and builds. Browser-scoped state and stateless plugin handlers must never create learner drafts, attempts, grades, analytics, or plugin execution/submission rows; normal submission routes never accept a preview flag.
- Long-running user actions use the shared blocking `ProgressDialog`. Report real completed/total progress when the operation exposes it; otherwise use its indeterminate state instead of a fabricated percentage. The dialog is non-dismissible while work is running and the operation's existing notification or terminal state remains responsible for success and failure details.
- Overlapping dialogs and full-screen editors use the shared `useBodyScrollLock`; never independently save and restore body overflow. Cleanup order may differ from opening order, and scrolling must resume only after the final owner closes. See [course-content scroll behavior](COURSE_CONTENT_TREE_IMPLEMENTATION_PLAN.md#phase-7-unified-teacher-content-tree---complete).
- The shared Monaco loader must use absolute, first-party asset URLs based on the browser origin. Root-relative paths load the editor but fail inside blob-backed language workers. See [frontend decisions](reference/PLATFORM_DECISIONS.md#frontend-platform-decisions).
- Code editors, rendered code, and Markdown code spans/fences must remain non-translatable. Editable code also disables browser autocorrection, capitalization, spelling, writing suggestions, and known writing-assistant hooks; do not apply those protections to ordinary instructional prose.
- User-facing text is localized. Subject teaching language—not the viewer locale—controls generated curriculum, rubric, and assessment-feedback language where documented. A separate optional Subject programming-language default, selected from the configured Judge0 runtimes, seeds new Programming Exercises created in that Subject's courses and banks; it never rewrites existing activities. Missing and multiple-language Subject values require an explicit exercise-level choice.
- Cookie-authenticated mutations enforce the configured browser origin. External execution services such as Judge0 and Playwright remain behind Cognelo server routes.
- Explicit course owners/teachers are course-wide; section teachers and TAs are section-scoped and never gain course management from a section assignment. A section teacher may manage that section's roster; section teachers/TAs may inspect, grade, export, and answer challenges only for assigned sections, but cannot release grades. Course designers who own a course may design it but need a global teacher role to grade. Explicit course-level TA assignment is rejected. Membership provenance distinguishes `explicit` from `section_derived`; `createdById` is provenance, never residual authority. Removal is symmetric and immediate, the final owner cannot be removed, and academic/audit history survives staff removal. Concurrent grade and feedback saves use optimistic conflict rejection. Student-triggered question authoring tries explicit course staff AI preferences in creator/owner/teacher order, skips unusable connections, and fails safely only after exhausting that ordered list. See [the role authorization and multi-teacher E2E plan](ROLE_AUTHORIZATION_E2E_IMPLEMENTATION_PLAN.md).
- Administrators configure execution services in the database under **Settings → Runners**, including Judge0, Web Design, and the reserved SageMath integration. Authentication tokens are encrypted with the instance credential key and never returned to browsers. The schema permits multiple runners per type; core currently selects the first enabled row behind a selector boundary reserved for future round-robin pools. Unsaved runner types appear disabled, require a valid HTTP(S) endpoint before they can be saved, and reject malformed URLs as validation errors rather than internal failures.
- Browser sessions use a rolling eight-hour HttpOnly cookie renewed by successful current-user checks. An unchanged successful focus/interval check must preserve the current user object identity so mounted course, gradebook, and activity data do not reload. Temporary network, server, or database failures must preserve the mounted authenticated workspace and retry; only a confirmed invalid session may clear the user and redirect to sign-in.
- Production schema changes require additive/idempotent migrations where possible, a fresh production-clone rehearsal, backups, explicit approval, smoke tests, and a documented rollback path. Use the combined `npm run db:migrate:all` path (`npm run db:migrate` is an alias); raw `prisma migrate dev` mistakes separately managed plugin tables for drift and must not be run against the shared database.
- Student groupings are section-scoped containers of teams, distinct from `CourseGroup` sections. A student may join only one team per grouping, with independent assignments across groupings. Use roster-management authorization for staff APIs; learners get a separate names-only My teams projection. Hidden groupings are excluded from learner reads and choices without deleting memberships. Persist the assignment method independently of visibility and show it in the teacher editor/cards. Per-team capacities bound random and student assignment. Student choices require confirmation and obey From/Until (Until is exclusive) plus change permission. Retain team IDs and advance grouping revisions on both teacher saves and student choices. Smart assignment is a disabled placeholder. Section removal deletes its groupings even when the roster moves. Activity exceptions reference stable team IDs; deleting a team removes its exception rules. Shared submissions remain unimplemented. See [Student groupings and teams](STUDENT_GROUPINGS.md).
