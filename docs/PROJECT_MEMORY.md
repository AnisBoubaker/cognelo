# Project Memory

This file is for platform-level memory only.

Plugin-specific behavior, persistence, routes, UX decisions, and implementation notes belong in the owning plugin package under:

- `packages/plugin-activities/plugin-*/README.md`
- `packages/plugin-activities/plugin-*/PROJECT_MEMORY.md`

## Long-Term Platform Decisions

- Use a monorepo with separate `apps/api` and `apps/web`.
- Keep auth, authorization, users, subjects, activity banks, courses, materials, and generic activity orchestration in core modules.
- Keep activity business logic out of course models.
- Store research metadata explicitly on bank activities, activity versions, course activity copies, and activity types as appropriate.
- Use Prisma/PostgreSQL with normalized tables and JSON fields only for extensible metadata/config.
- Keep the first version as a modular monorepo, not a microservice split.
- Favor shared contracts and service-layer logic over duplicating validation in each app.
- Treat `docs/PROJECT_MEMORY.md` and `README.md` as living project artifacts that must be updated whenever platform architecture, setup, product behavior, or major cross-cutting capabilities change.
- Treat plugin `README.md` and `PROJECT_MEMORY.md` files as living plugin artifacts that must be updated whenever plugin behavior or plugin-local architecture changes.
- Linked course activities support explicit bank synchronization. Retrieval preserves course-only placement and assignment state; course-to-bank publication creates a new immutable version and requires bank write access. No synchronization mutation is allowed after even a draft core attempt exists, and deleting the bank clears provenance links so the action disappears.
- Bank activity version comparison is a generic core capability exposed from each eligible activity row's actions menu, not from the already-busy activity editor. Core returns a shared semantic/structured diff model and `@cognelo/activity-ui` renders it consistently; plugins do not need to implement ordinary config diffs. Historical plugin-private data is intentionally excluded until private authoring is stored per immutable `ActivityVersion`.
- Shared string diffs must preserve carriage returns/newlines, render contextual line hunks instead of complete changed documents, and highlight the exact changed character span. Markdown question sources use `##` headings as contextual boundaries so an MCQ change shows its containing question rather than the entire source.
- Every synchronization mutation requires a second, action-specific confirmation. Bank-to-course retrieval prominently warns that replaced course-local authoring is unrecoverable; course-to-bank publication explains that prior bank versions remain recoverable in immutable version history.
- The Coding Homework Grader scaffold is registered as `coding-homework-grader` in `packages/plugin-activities/plugin-coding-homework-grader`; its phased implementation plan lives in `docs/CODING_HOMEWORK_GRADER_IMPLEMENTATION_PLAN.md`, and plugin-local design choices belong in that package's `PROJECT_MEMORY.md`. Its persistence foundation, teacher authoring data, prior-documentation snapshot/extraction behavior, C parser adapter, ZIP preflight/final-submission validation, submitted-function candidate analysis, challenge question generation, student challenge answers, and preflight/final submission records are plugin-owned through a local Prisma schema, generated client, activation migration manifest, plugin routes, and bank-to-course copy hook rather than core Prisma tables. It consumes course content through generic content type plugin extraction/vector-search interfaces, so content-specific parsing and prior-content vector storage remain in content type plugins/platform services.

## Plugin Architecture Rules

- Activity plugins should be clearly packaged under `packages/plugin-activities/plugin-*`.
- Plugin-owned code should not be scattered through core modules or the main web app when it can live inside the plugin package.
- Plugin-specific persistence should be modeled as plugin-owned tables/modules rather than by stretching core tables with plugin-specific columns.
- Plugin-specific HTTP handlers should live in plugin packages. The API app should expose generic dispatcher routes, not one hardcoded Next route file per plugin capability.
- Generic plugin dispatchers enforce authorization before plugin code runs: course activity routes are manager-only, bank routes are bank-manager-only, assigned group routes rely on authorized group/assignment access, and unsafe content-resource plugin methods are course-manager-only. Activity and content route registrations without explicit supported type keys do not resolve.
- Shared plugin-facing UI belongs in `packages/activity-ui`.
- Contextual action menus use the shared portal-based `ContextMenu` from `@cognelo/activity-ui`, not page-local absolutely positioned containers. It escapes ancestor overflow, flips/clamps within the viewport, and closes consistently on outside interaction, Escape, scroll, or resize. Activity-bank, course-content, course-group, and account menus use this primitive. A repository guard scans page and plugin TSX so raw action menus cannot be introduced there; selection listboxes and full dialogs remain separate controls.
- Shared plugin registries belong in `packages/activity-sdk`.
- Content type plugins expose extracted embedding/reference documents through the shared server-side `getEmbeddingDocuments` hook. Activity plugins should call core dispatchers for this data rather than importing or branching on concrete content type plugins.
- Vector storage and similarity search are shared platform capabilities, not a Coding Homework Grader-only feature. Content type plugins should own extraction/chunking semantics and invalidation decisions behind the `indexEmbeddingDocuments`/`searchEmbeddingDocuments` interface, while production persistence/search should move to common platform pgvector tables rather than one table per content plugin. Activity plugins should request vector similarity through core/content-plugin dispatchers instead of reading vector tables directly. The current dev implementation uses deterministic embeddings and plugin-owned metadata indexes only as temporary lightweight infrastructure. Before pgvector migration, decide the first embedding model, vector dimensions, model/version table strategy, whether submitted homework functions share the same tables, index type, fingerprint invalidation rules, and sync vs background indexing.
- Untrusted learner code must run in an external sandbox service, not inside the Cognelo API process.
- Cross-app notifications should use the shared notification service from `@cognelo/activity-ui` (`NotificationProvider` mounted in the web app, `useNotifications()` in core and plugin UI) rather than per-form inline success banners.
- Cookie-authenticated unsafe API requests use centralized Origin-based CSRF protection. The request `Origin` must exactly match the configured `CORS_ORIGIN`; safe methods and requests without a session cookie are not blocked by this check.

## Implemented Platform Foundations

- Authentication uses JWT stored in HttpOnly cookies. JWTs carry the user's authentication version; administrator password resets increment the persisted version so every older token is rejected.
- Global authorization supports many-to-many user roles (`admin`, `course_manager`, `teacher`, `student`) and is designed for more roles later.
- Users have account-wide profile settings with editable first and last name fields. Email changes are intentionally admin-only.
- The authenticated account menu shows `Cognelo ver. …` beneath Logout. The web build derives the value from `git describe` against `cognelo-*` release tags, retains commit and dirty-checkout metadata for non-release builds, accepts a build-time `NEXT_PUBLIC_COGNELO_VERSION` override, and falls back to the web package version when Git metadata is unavailable.
- Administrators manage users under `/settings/users`. The admin-only API supports filters for role, first name, last name, and email plus server-side page/page-size pagination (10 rows by default; supported sizes 10, 25, 50, and 100); creates active accounts with an initial password; edits first name, last name, email, and one-or-many global roles; displays email-verification status; and sets temporary passwords for other users. A reset sets `mustChangePassword`, increments `authVersion`, rejects prior sessions, and forces the next login through `/change-password`; while restricted, only current-user lookup, password replacement, verification, and logout remain available. Administrators use the normal profile flow for themselves.
- AI agent/model connection settings are account-wide. Personal connections are owned by a user; global connections have no owner and are admin-managed for later teacher/course use.
- Core exposes course-scoped AI helpers for server-side plugin work. `Course.metadata.aiSettings.studentSupportAiAgentConnectionId` remains the course student-support setting. Coding Homework Grader challenge generation resolves a course teacher/owner's question-authoring AI preference for student-triggered generation instead of using a student-owned or local student-support connection.
- Accounts can be activated on first login when a person was pre-added to a group participant list by email and no user record existed yet. Newly self-activated accounts must then verify their email at `/verify-email` before normal application access. Verification uses a six-digit HMAC-hashed code with a 10-minute lifetime, 60-second resend cooldown, and five-attempt limit. The verification email follows the current UI locale (`en`, `fr`, `zh`, or `ar`), including RTL HTML for Arabic, and safely defaults to English when no locale is supplied. Existing accounts are grandfathered by the migration, seed accounts and the production bootstrap administrator start verified to avoid deployment lockout, and an administrator changing an account email clears its verified state. The explicit student CSV assigned-password mode is the exception for pseudonymous rosters: it creates an active linked account with `emailVerifiedAt` set, `mustChangePassword = false`, and no verification message, allowing immediate login with the teacher-distributed password.
- Courses support create, edit, archive, and draft/published/archived status.
- Users have a generic `metadata` JSON field used for account-level preferences, including the selected AI agent for question authoring help.
- Courses have a generic `metadata` JSON field used for course-level settings, including the selected AI agent for student support.
- Subjects are first-class curriculum containers. A subject stores a teaching language constrained to Cognelo’s supported locales and can own subject-level materials, activity banks, courses, and one subject-scoped knowledge graph.
- Subject knowledge graphs use normalized core `SubjectKnowledgeConcept` and `SubjectKnowledgePrerequisite` rows. Concept positions and manually selected source/target handles are persisted for visual authoring. A prerequisite edge is directed from the concept that requires knowledge (`sourceConceptId`) to the required concept (`requiredConceptId`). Core rejects self-links, duplicates, cross-subject endpoints, and cycles. The Subject edit UI uses React Flow for node authoring, connections, endpoint reconnection, pan, zoom, minimap, and viewport controls; its workspace can be resized vertically from a 500px minimum up to 1200px. Selecting a concept in either editor or preview highlights and fully emphasizes outgoing prerequisite edges/direct targets in teal and incoming edges/direct sources in violet, follows only outgoing dependent-to-prerequisite edges to retain the complete transitive prerequisite chain at full emphasis, and dims concepts outside those sets. All graph changes remain in the Subject form draft, participate in the shared unsaved-change guard, and persist atomically with Subject metadata through the main `PATCH /subjects/:subjectId`; the editor can restore the graph version loaded from the server. Multiple outgoing and incoming edges without explicit handles are deterministically fanned across four handles, while selection elevates the chosen edge above overlaps. The Subject detail UI shows a 600px-tall read-only preview whose viewport remains pannable and zoomable.
- Knowledge skills are stable `SubjectKnowledgeSkill` rows with identity, title, position, and active/retired state. `SubjectKnowledgeConcept.skills` remains a synchronized newline-delimited compatibility projection for older/AI graph contracts. Each skill is something the learner can perform or an observable learning goal. AI graph generation requests concise assessable actions, requires at least one per generated concept, and generated drafts receive stable client IDs before save.
- The editable knowledge-graph workspace has a draggable vertical separator between the graph canvas and concept/skills inspector. Pointer dragging resizes the inspector from the left edge; keyboard Left/Right adjusts it in steps, Home/End selects its limits, and double-click restores the default. The layout preserves minimum graph/inspector widths and collapses back to the existing stacked mobile layout below 800px.
- Linking activities to subject knowledge concepts is a mandatory core capability for every activity type, not a plugin opt-in. The host wraps bank and teacher course activity authoring in Activity/Concepts tabs, including unsupported/future renderer cases. Teachers may save an empty selection. Core stores normalized `BankActivityKnowledgeConcept`, `ActivityVersionKnowledgeConcept`, and `ActivityKnowledgeConcept` rows; validates that every selection belongs to the activity's subject; snapshots bank selections with every new version; copies version links to a course activity on assignment; and thereafter lets the course copy diverge independently.
- Authoring-time AI generation for MCQ, Parsons, and coding exercises shares three knowledge modes. Every mode sends the complete subject concept/skill catalog to the generation model as a curriculum boundary. `selected` additionally steers generation with the current on-screen skill draft, including unsaved choices; `suggest` ignores the current selection and maps generated content to exact skills from the subject catalog; `ignore` neither reads nor changes knowledge selections and performs no post-generation mapping. Suggested links always store explicit skill snapshots (`selectsAllSkills = false`) and update only the host Concepts-tab draft until the teacher saves it. Activity and Concepts panels stay mounted across tab switches so generated/edited activity content is preserved. Saving either tab uses one logical save boundary and includes both the activity payload and current knowledge-selection draft when activity content is dirty.
- Activity concept selection distinguishes whole-concept intent from exact skill intent. Links store `selectsAllSkills`, stable `selectedSkillIds`, and title snapshots. Checking a concept sets whole-concept intent while snapshotting its current IDs/titles; explicit skill selection remains distinct even when every skill is checked. The selector keeps its prerequisite-based ordering and two-pane UX. Manual skill deletion is immediate after a shared confirmation dialog: current bank/course mappings can replace the skill with another active skill in the same concept or remove it, while immutable versions remain unchanged. Manual concept deletion removes current mappings and graph edges with no replacement option. AI graph generation is the only draft-save exception: its exact disclosed concept/skill removals may be submitted with the graph and applied transactionally on Subject save; any persisted omission absent from that list still triggers the deletion guard. Persisted concepts/skills are retired rather than physically erased, and every attempt snapshots its resolved activity skill mapping at start.
- Student-model implementation is planned in `docs/STUDENT_MODEL_IMPLEMENTATION_PLAN.md`. The agreed direction separates append-only normalized learning evidence, rebuildable versioned inference, and interventions; begins by replacing string-only subject skills with stable identities and immutable activity/attempt mappings; keys the initial model by `CourseGroupParticipant`; uses raw demonstrated outcomes rather than late penalties or gradebook selection policy; and targets a teacher-only stable-skills → summative-evidence → weighted-Beta-state → skill-matrix vertical slice before formative evidence, student views, recommendations, or more complex models.
- On desktop, the activity concept selector has a viewport-aware fixed working height and independently scrollable concept and skill panes, so selecting a concept deep in a long list does not move its skills off-screen. Changing the active concept resets only the skills pane to its top. Selector checkboxes override the platform's full-width text-input styling with explicit native checkbox dimensions; on narrow screens the panes return to the stacked document flow.
- Subject knowledge-graph AI generation follows the shared question-authoring agent preference and appears only when the user has selected an enabled agent. The collapsed editor section accepts optional private directions, a maximum of 1–50 concepts, and `new` or `iterate` mode. Empty graphs default to `new`; non-empty graphs default to `iterate`. New mode excludes and explicitly ignores the current graph, requiring confirmation before replacing a non-empty draft and conditionally warning when current activities use items that replacement will remove. Iterate mode sends the complete current unsaved concept/edge/skill draft and instructs the model to return the complete revised graph while reusing stable concept keys where possible. Returned concepts with a retained key keep their ID, and exact retained skill titles within those concepts keep their skill IDs; renamed items are deliberately reported as one deletion plus one addition. Every iteration opens an informational dialog with only an OK action, listing concept/skill additions and deletions and conditionally warning that current activity links will be removed on save. Both modes use the current form description and teaching-language selection (not the viewer’s interface locale), and allow the model to return fewer concepts. Core falls back to the Subject’s saved teaching language when no valid selection is supplied. It validates JSON shape, concept limits, at least one skill per concept, references, lengths, duplicate concepts/edges, self-links, and cycles, retrying invalid output up to three model calls. A valid result receives a prerequisite-level layout and is returned as an unsaved draft; only the main Subject Save action transactionally persists it and the exact AI-disclosed removals.
- Subject graph draft layout uses `elkjs` and offers hierarchical, forest (`mrtree`), radial/star, force-directed, and compact layered presets. Disconnected components remain valid and are laid out separately. ELK receives layout-only prerequisite-to-dependent edges so foundations appear first, while the persisted/displayed edge direction remains dependent-to-prerequisite. Re-layout changes only draft positions, triggers unsaved-change protection, fits the editor viewport, and can be reverted before saving.
- Subject descriptions use the canonical shared Markdown-backed `RichTextEditor` in both create and edit forms. Stored Markdown is rendered with the sanitized shared `MarkdownRenderer` on the subject detail page rather than displayed as raw syntax; subject list rows omit the description to stay compact.
- Subject editing presents metadata and knowledge-graph authoring in separate Information and Knowledge graph tabs. Tab changes are local UI state and do not persist or discard the shared subject draft. A responsive sticky action bar remains available on either tab, exposes the combined dirty state, and persists both tabs through the same Save action.
- React Flow remains mounted while the Knowledge graph tab is hidden so unapplied inspector edits and viewport state survive tab changes. Because a hidden panel has no measurable canvas, the graph performs one deferred initial `fitView` the first time that tab becomes visible; later tab changes, ordinary pan/zoom, and inspector resizing must not reset the teacher's viewport.
- Activity banks are first-class authoring spaces related to a subject and owned by an individual. Admins can later change ownership and sharing rules.
- Activities are authored in activity banks as `BankActivity` records with version snapshots in `ActivityVersion`.
- Adding an activity from a bank to a course creates a course-local `Activity` copy from the selected/latest `ActivityVersion`.
- Course activity copies keep `bankActivityId` and `activityVersionId` for provenance, but they are not live references.
- Editing a course activity changes only that course copy and what students in that course see.
- Editing a bank activity creates a new version for future course assignments and does not affect existing course copies.
- Plugin copy contract: if a plugin owns private bank-owned data, it must copy that data into course-owned plugin tables through `onCourseActivityCreatedFromBankVersion` when a course activity is created from a bank version. Core only copies the generic `Activity` row and `ActivityVersion` data; plugin-owned tables are the plugin's responsibility.
- New plugins or plugin schema changes that introduce bank-owned private data must include a bank-to-course copy hook and manual verification that the copied course activity has independent plugin-owned rows.
- Plugin delete contract: if a plugin owns bank-owned private data, it must clean those rows through `onBankActivityDeleted` when a bank activity is deleted. Course-owned copied plugin rows must remain intact.
- Deleting a bank activity that is used in courses is allowed only after a second confirmation. Existing course activities lose `bankActivityId` / `activityVersionId` through database `SetNull` relations and become fully course-local copies.
- Activities remain plugin-style registry entries and are not hardcoded into course models.
- The activity registry now distinguishes `core` and `plugin` providers. Plugin-backed definitions retain installation/activation/dispatch behavior; core-backed definitions reuse generic Activity infrastructure without masquerading as installable plugins. The first core definition is `test`; it is enabled for its dedicated course creation flow but rejected by generic plugin activity creation/update routes.
- Compound Test implementation is tracked in `docs/TEST_COMPOUND_ACTIVITY_IMPLEMENTATION_PLAN.md`. Phases 1-6 are implemented: explicit `ActivityType.providerKind`/`providerKey`, normalized core `Test`/`TestItem`/`TestItemAttempt` persistence, immutable `TestRevision`/`TestRevisionItem` attempt snapshots, dedicated Test authoring with local or bank-owned child composition and safe duplication, containment and lifecycle-safe deletion, assignment/content integration, a dedicated student execution shell, parent grade aggregation, item-level manual adjustment, individual review, and extensible aggregate review. A Test is summative, reuses one outer assignment/content placement/gradebook item, and starts one `core:test` parent attempt whose manifest owns generic child state/results. Activity definitions opt in through `supportsCompositeExecution`; server submission/action handlers and web embedded/review renderers are keyed registries, so future plugins add adapters without changing the Test schema or core orchestration. Embedded activities only load/autosave state and never submit individually. MCQ, Parsons, coding exercise, and web-design coding exercise are supported adapters; the single **Submit Test** action grades all saved child states and then submits the parent. Server-authoritative deadlines, localized automatic finalization, session-based no-resume enforcement, repeated-submit idempotency, and a unique submission claim protect the finalization path. Coding homework grader remains excluded until its ZIP/preflight/manual-review workflow has a compatible composite contract.
- Course managers can remove activities directly from the course detail page.
- Gradebook Phase 1 core schema foundation is present in core Prisma: `GradebookItem`, `ActivityAttempt`, `Grade`, and `GradeEvent`. A gradebook item is one assigned group activity (`CourseGroupActivity`) and grades/attempts attach to `CourseGroupParticipant` with optional linked `User`. Plugin-specific attempt artifacts remain plugin-owned; core owns normalized attempt/grade/audit metadata.
- Gradebook Phase 2 lifecycle wiring creates a `GradebookItem` whenever a `CourseGroupActivity` is materialized through direct group assignment, course-wide all-groups assignment, or future-group inheritance of an all-groups rule. Removing the all-groups policy leaves those gradebook items intact because the underlying group assignments remain intact.
- Gradebook Phase 3 core services live in `packages/core/src/gradebook.ts`. They start numbered attempts for assigned group activities, enforce max-attempt and due-date attempt limits, compute lateness on submission, record grading results, and write grade audit events. Plugins can use `getAssignedGroupActivityAttemptSource` from the activity SDK to convert assigned group plugin route context into the core attempt service input shape.
- Unfinished standalone student work uses core `ActivityResponseDraft` rows keyed by assigned activity and `CourseGroupParticipant`. Draft saves are serialized in the web state host, are bounded to 2 MiB, do not create or consume gradebook attempts, and are cleared after successful final submission. Standalone MCQ, coding-exercise, and web-design coding exercise renderers use this host; Parsons and Coding Homework Grader retain their richer plugin-owned persisted drafts. Core Test shells are explicitly rejected by the standalone draft service because Test children autosave through `TestItemAttempt` and the parent Test save queue.
- Gradebook Phase 4 grading contracts are in the activity SDK. Activity definitions can declare grading capabilities, manual grading renderer hints, and plugin grading result payloads. Parsons is the first integrated plugin: it declares attempts/auto/manual grading support and exposes a server grading handler that converts stored Parsons evaluation results into core-compatible raw scores and analytics payloads.
- Gradebook Phase 5 normalization/selection is handled in `recordActivityAttemptGradingResult`. Core scales raw plugin scores to `GradebookItem.pointsPossible`, computes pass/fail from item thresholds, applies late penalties, reconstructs graded attempt history from `GradeEvent` snapshots, and selects the current `Grade` using latest/best/first/weighted-average strategies.
- Gradebook Phase 6 teacher UI is consolidated in the course Gradebook tab. The API route `GET /api/courses/:courseId/gradebook` returns participant-by-assigned-activity rows, supports group/activity/status filters, and exports CSV with `format=csv`. Missing work is represented by rows for student participants without grades or attempts.
- Global outbound email configuration lives at `/settings/email` and is admin-only. The supported delivery technologies are a vendor-neutral SMTP relay and Microsoft Graph using OAuth 2.0 client credentials; local Sendmail/MTA delivery and vendor-specific REST adapters are intentionally excluded. `EmailDeliveryConfiguration` stores the selected sender and route, while SMTP passwords and Graph client secrets are AES-256-GCM encrypted using the instance-specific `EMAIL_CREDENTIALS_ENCRYPTION_KEY` and never returned by API DTOs. That same instance key protects one-time verification code hashes. The admin test message may go to any valid address. The reusable non-test core send path accepts only active users or unclaimed `CourseGroupParticipant` emails awaiting activation; first-login email verification is the first product use, while other account and notification triggers remain future work. Microsoft Graph requires `Mail.Send` application permission with administrator consent, and Microsoft 365 may source the visible display name from the sender mailbox profile.
- The course-level teacher gradebook renders activity-level summary rows rather than defaulting to all student/group rows at once. Each activity row shows submission count, graded count, mean grade, release/hide for all assigned groups, a detailed-results link, and an expandable per-group summary with group-specific release/hide controls and group-scoped detailed-results links. Detailed activity results live under `/courses/:courseId/gradebook/activities/:activityId` and can be scoped to one section/group with `?groupId=:groupId`. Back links always return to the course Gradebook tab and preserve the group filter when present; manager-facing group gradebook navigation is retired.
- Assigned group activities have `assessmentMode` metadata. Formative activities keep plugin checks/events for analytics without creating core submissions or grades. Summative activities expose plugin submission flows; for Parsons, submit creates a core attempt, submits it, and records an automatic grade from the Parsons evaluation without showing correctness feedback to the student. New assignments default to formative unless the teacher selects summative. Summative assignment forms expose core gradebook policy settings and persist them to `GradebookItem`: points possible, points/pass-fail mode, pass threshold, attempt limit mode, max attempts, grade strategy, and drop-lowest for weighted averages. If the summative attempt limit is reached, Parsons returns the completed attempt read-only instead of creating a new attempt.
- Gradebook Phase 7 student visibility is implemented. Teachers release or hide the final grade for each `GradebookItem`; release/hide changes write participant-scoped grade audit events. Before release, repeatable summative items (`unlimited`, `until_due`, or `max_attempts > 1`) expose the authenticated student’s latest provisional normalized result and plugin-supported own-attempt review so it can guide another attempt. Releasing publishes the final grade selected by the item’s latest/best/first/weighted strategy and prevents further attempts. Single-attempt summative grades remain hidden until release. The section/group Grades endpoint and activity surfaces do not expose raw plugin grading payloads or hidden Test details; released Parsons grades include sanitized deterministic feedback and grading breakdowns.
- Parsons exposes a teacher-only gradebook attempts route through the assigned group plugin dispatcher at `parsons/gradebook-attempts`. The detailed activity results page uses it for the "See answer" overlay, showing submission snapshots by default and optionally including non-submission attempts/events.
- Gradebook Phase 8 manual grading/regrading is implemented. The detailed activity results page resolves plugin-specific manual grading renderers through the activity definition `manualGrading.rendererKey`; Parsons provides the first panel, combining submitted answer review, attempt/event navigation, teacher override score/reason fields, and the existing regrade action. The detailed activity results page also supports bulk Regrade All for submitted/graded attempts and a Grade All Manually page that pages through student attempts 10 at a time. Moving pages or pressing Save persists all visible manual grades and editable student-facing feedback.
- Teachers can delete a specific submitted/graded attempt from the detailed activity "Grade manually" overlay. Core soft-deletes the `ActivityAttempt`, records a `submission_deleted` grade event with the deleted attempt snapshot and reason, and excludes deleted attempts from active submission counts, grading actions, and non-override grade display. If deletion leaves no active submitted attempts, the participant row is shown as missing/did-not-submit rather than retaining a stale attempt-derived score; explicit override grades may remain visible without an active attempt.
- Course content tree Phases 1-10 are implemented. Core Prisma has `CourseContentItem` and `CourseContentItemKind` for the shared folder/material/activity placement tree. Folders are generic course-level structure (`groupId = null`) preserved across groups; group-specific materials and activities may be placed inside those shared folders. Core service logic in `packages/core/src/course-content.ts` creates folders, material items, and activity items; validates course-level parent folders, course/group scope, and folder cycles; computes effective visibility; and lists all or student-visible content. Group content listing returns the shared course structure plus the selected group's content items. When an activity has both a shared course placement and an assignment-backed placement for the selected group, the shared placement remains the returned row and receives the selected `courseGroupActivityId`; the materialized group placement is suppressed. This keeps inherited folder/order and group visibility overrides on one actionable identity while preserving the assigned-activity link. API routes under `/api/courses/:courseId/content` and `/api/courses/:courseId/groups/:groupId/content` expose course/group content listing, folder creation, material placement, activity placement, update, and delete. The tree is a placement/order/visibility layer only: materials remain resources, activity availability remains assignment policy, and activity plugin behavior remains isolated behind generic `Activity` and `CourseGroupActivity` references.
- Course content tree Phase 4 is dev-seed driven because there is no production content to preserve. `packages/db/prisma/seed.ts` creates a representative mixed content tree for Programming 101 / Section A with visible and hidden course folders plus materials and activities placed side by side. Existing material/activity tables remain intact while the new tree is exercised through seeded `CourseContentItem` rows.

The seed reads `tmp/INF155-A2023-TP1.pdf` with `pdftotext` when available, copies it into plugin storage as a deterministic assignment PDF attachment, uses `tmp/FichiersFournis` to build starter-file documentation, and stores C labyrinth prompt/requirements in plugin-owned course and bank tables. - Course content tree activity placement is implemented at the service/contract layer. `ActivityInputSchema`, `CourseGroupActivityInputSchema`, and all-groups assignment input accept optional `contentPlacement`. Course activity creation can create a course-scoped activity content item. Direct group assignment can create a group-scoped content item in a selected shared course folder. Course-wide all-groups assignment stores placement metadata and materializes activity content items for current and future groups using the same shared course folder IDs. When configuring an all-groups assignment for the first time, its folder and visibility default to the activity's existing course placement; migration `202608090001_inherit_course_wide_activity_placement` repairs legacy all-groups rows that were unintentionally materialized at the root.
- The teacher course page picker is a course-element picker with Activity banks, Material, Programming, and Miscellaneous tabs. It loads shared course folders, lets teachers choose destination folder and visibility, creates course-level folders, creates plugin-backed content resources from enabled content type definitions, and sends `contentPlacement` for local or bank-backed course activity creation. The course page is the canonical teacher content workspace: a compact Course/Group perspective selector after the tabs reloads the same Content panel with the selected group's effective tree. Only the active perspective expands: Course shows its word while Group is icon-only; activating Group collapses Course to its icon and reveals the group dropdown. Group activation immediately opens the last valid group selected during the current mounted course page, or the first alphabetical group when none is remembered. Reloading the browser resets Group mode to that first alphabetical group. Group-facing lists are alphabetized with locale-aware numeric comparison, and selector option labels are capped at 20 characters with an ellipsis while preserving the full title as hover text. Future Student perspective support must use the same active-expanded/inactive-icon pattern. Course mode owns creation, settings, ordering, and removal. Group mode is visibility-only and exposes neither drag handles nor remove actions. Manager visits to legacy group URLs redirect to that selected course perspective, while student group routes remain intact.
- Student group workspaces render one Content tab backed by the group content endpoint. Effective visibility filters hidden items and descendants of hidden folders before they reach the browser content tree, and the non-manager group detail payload omits the corresponding assignment records. Non-manager assigned-activity resolution enforces that same effective visibility, so direct assigned-activity and plugin-route requests cannot bypass a hidden placement or hidden ancestor. First-level folders render as theme-colored accordions with localStorage persistence keyed per course/group; nested folders keep normal folder-row expand/collapse. Student activity rows carry availability, submission, and released-grade badges, while grade release remains controlled by gradebook APIs.

Content type plugin installations mirror activity plugin lifecycle behavior: discovered plugins sync as inactive/disabled, admins activate them before enabling creation, activation can create or restore plugin-owned tables, deactivation backs up owned tables, disabled-but-active plugins may still serve existing resources, and inactive plugins are blocked. `/settings/plugins` is the shared plugin admin surface with separate Activity plugins and Content type plugins tabs. Generic course/group content resource API routes create/update/delete/list plugin-backed resources and dispatch resource plugin routes through active-plugin, authorization, and non-manager content-tree visibility checks. The old material tables, routes, and `materialId` fields remain compatibility-only for older local records and downloads, but new canonical course content creation should use `CourseContentResource`. Seed data now creates representative GitHub repo, File, and Text content as plugin-backed resources and deletes the old seed material rows. The GitHub repo content plugin owns GitHub picker metadata, validation/normalization, server create/update/open/embedding-document handlers, and its settings form; it stores `{ url }` in generic content resource metadata. The File content plugin owns file picker metadata, upload settings UI, local file upload/download plugin routes, file metadata, and file embedding-document extraction; it stores file metadata in generic content resource metadata for now. The Text content plugin owns text picker metadata, text settings UI, body create/update behavior, viewer/open-action declaration, and text embedding-document extraction; it stores Markdown body data in generic content resource metadata for now. None of the current concrete content type plugins require plugin-owned tables yet. The plugin authoring handbook now covers both activity plugins and content type plugins, including a simple content type plugin tutorial.

## Naming Model

- The user-facing product concept formerly called a course group should move toward "section".
- The current database/service name remains `CourseGroup` during this transition.
- Use "section" in new product copy where feasible, but be careful when referencing existing code paths that still say `groups`.

## Group Participant Decisions

- Course sections/groups have explicit participant records separate from platform users.
- The course Participants tab replaces the former Groups tab and renders every group with its participants inline. Group create/edit and participant enrollment use modal dialogs, and routine management no longer links to a separate group workspace. Student rosters are imported from a browser-local, headerless CSV in one of two explicit formats selected by the teacher: `first name,last name,email[,external ID]`, or, when **CSV includes assigned passwords** is checked, `first name,last name,email,password[,external ID]`. The parser never guesses between these formats. All imported records use the `student` role, every email is validated, assigned passwords require 8–200 characters, validation blocks the complete import until every row is valid, and emails already present in the destination group are skipped. Assigned-password rows create active verified accounts and link all pending participant rows for the same email. An existing active, verified account with no forced password change is linked only when the supplied password matches; otherwise the row fails, and Cognelo never changes that account's password. The final course group is protected in both UI and core. A group with no student participants needs one confirmation; otherwise deletion requires either a destination group, with participant emails deduplicated, or a second permanent confirmation that cascades group-scoped attempts/grades and removes student course membership only when the learner belongs to no other course group.
- Section/group participants support roles `student`, `ta`, and `teacher`.
- Adding a participant by email links immediately to an existing user when the email already exists.
- When the participant email matches an existing user, first name, last name, and external ID are treated as locked/read-only in the add-participant UI.
- When the participant email does not match an existing user, the group participant record is created without a linked user account, and the actual user account is created only at first activation/login.
- Group creators are automatically added as `teacher` participants when a group is created.
- A manager cannot remove themselves from the participant list of a group.
- Existing-user lookup for participant enrollment is manager-only and happens before submit in the group participant UI.
- Non-manager access to a group is tied to being added as a participant in that group, not only to broad course visibility.
- Student-facing navigation should be section-first: students work from the section workspace, not the broad course workspace.
- Student course access should resolve to visible published sections/groups, and the course detail page should not act as the primary student workspace.
- Student access to assigned activities should be section/group-scoped and assignment-aware rather than relying on course-level activity routes.
- Generic bank and course activity descriptions allow up to 30,000 characters because the description is the student prompt and may contain a complete reading passage; plugin-specific generation inputs may use that same limit when the prompt is model context.
- Student access to inherited course file materials from a section/group should respect section/group visibility rules and use section/group-scoped download routes.
- Teachers can assign a course activity to all current and future groups from the course activity list. The course-level rule is stored on the course activity metadata, but it materializes as real `CourseGroupActivity` rows for each group so grading and later group-scoped records can stay attached to the group. Course-wide assignment policy includes `enablePerGroupSettings` and `assessmentMode`: when per-group settings are true, existing group availability dates are preserved and group pages can edit dates; when false, course-level availability replaces group dates and group-local date edits are blocked. Group-local screens must not allow removing assignments whose metadata marks them as course-wide all-group assignments. The course content perspective owns ordering; the Group perspective does not reorder assignments. Removing the all-groups rule from the course page must leave existing `CourseGroupActivity` rows in place and remove only the course-wide metadata marker, converting them back to normal group-managed assignments.

## Course Material Decisions

- Course materials are generic typed records with extensible metadata.
- Implemented material kinds currently include at least `folder`, `github_repo`, and `file`, with room for more later.
- Uploaded files are stored locally for MVP/dev and represented as `file` materials with metadata such as original name, stored name, MIME type, and size. Course/group content rows use that MIME type to select semantic PDF, office, media, archive, code/text, or generic-file icons from the centralized Tabler layer.
- GitHub repository materials are validated as `github.com` URLs.
- Course material records may still carry legacy `parentId` and `position` fields for compatibility, but `CourseContentItem` is the canonical student-facing hierarchy, ordering, and visibility layer.
- Material tree operations and compatibility code must still prevent moving a legacy material folder into one of its own descendants while the legacy fields remain.

## Frontend Platform Decisions

- Subjects and activity banks are top-level navigation items alongside courses.
- The subjects section follows the same list-first management pattern as other sections: `/subjects` shows the subject list with an Add action, `/subjects/:subjectId` shows linked activity banks/courses, and `/subjects/:subjectId/edit` edits subject metadata.
- `/subjects/:subjectId/edit` owns the visual knowledge-graph editor directly after the description. `/subjects/:subjectId` shows only the graph preview after Activity banks and Courses. Keep knowledge concepts subject-scoped until an explicit future migration introduces reusable cross-subject knowledge identities.
- Activity bank authoring pages should open the full plugin authoring UI, not only generic metadata.
- Activity rows inside a bank remain directly clickable and open the activity editor; the row Actions menu is layered above the row link so Edit, Duplicate, Move, and Remove remain independently operable.
- Activity-bank activity deletion is exposed through the row Actions menu and uses the shared confirmation dialog. If the activity is referenced by courses, forced deletion requires a second impact warning and preserves those course-local copies while removing their bank/version links.
- Activity-bank activity Actions also support Duplicate and Move. Duplicate opens a title dialog defaulted to the source title plus ` (copy)`; an existing terminal copy suffix increments to ` (copy #2)`, ` (copy #3)`, and so on. It then appends a new independent unpublished draft with no versions, copies knowledge selections and plugin-owned private authoring data through the shared `onBankActivityDuplicated` hook, and creates no source/course traceability links. Its first publish creates version 1. Move preserves the activity identity, versions, concept links, and plugin rows while appending it to another writable bank under the same subject. Destination authorization and subject matching are enforced server-side.
- Bank version history records publication milestones, not editing keystrokes. Draft saves create no version. Saving changed authored content while explicitly Published creates the next immutable version; publishing an unchanged snapshot reuses the latest published version. Pausing/archiving creates no version, and `currentVersionId` remains the latest published snapshot while draft changes may exist.
- The activity-bank list uses a button/dialog for creation and shows Edit/Delete row actions only for banks the current user can manage (currently owners and admins; future sharing can extend the server-provided `canManage` capability). A bank subject can change only while the bank is empty. Populated-bank deletion either moves activities in order to another writable bank under the same subject or requires a second destructive confirmation; deleting contents preserves course-local copies while clearing their bank/version links.
- Activity bank and course activity creation use picker dialogs grouped by activity categories. The permitted category IDs and label keys live in `@cognelo/activity-sdk/categories`; platform-owned localized category labels live in the web locale files under `apps/web/src/lib/i18n/messages/*`. Plugin activity definitions declare `defaultCategoryIds` from that list. Unknown category IDs fall back to `generic`. The special `all` token may be included in the array, such as `["generic", "all"]`, to show an activity in every visible category while still giving it an explicit home category.
- Plugin activity definitions declare default picker metadata such as default category membership and a semantic icon name. The web app renders interface, activity, and content-type icons through the centralized Tabler-backed `apps/web/src/components/app-icon.tsx`; pages must not add bespoke interface SVGs. Activity-bank pages read icon metadata from registered definitions instead of hardcoding plugin activity keys. Parsons uses the tornado icon.
- Bank activity authoring pages must resolve plugin-specific authoring UIs through the app activity renderer registry, not by importing plugin packages or branching on plugin activity keys in route components.
- Installed activity plugins are represented by `ActivityPluginInstallation` records. Newly discovered plugins start inactive and disabled. Admins activate a plugin first, then explicitly enable it for activity creation/use.
- Plugin-specific persistence is owned by plugin-local Prisma schemas, migrations, clients, and database modules. The core Prisma schema should not add plugin-owned activity data models.
- Plugin activation syncs activity type records and validates that plugin-owned tables exist. Plugin-local migration statements can create fresh empty plugin-owned tables during activation when the admin does not restore a backup.
- Plugin deactivation disables the plugin and renames its plugin-owned tables into backup tables recorded as `ActivityPluginTableBackup` rows. Reactivation can restore an unrestored backup for the same plugin version.
- Disabled or inactive plugins are removed from activity type listings, hidden from renderer selection for existing activities, and blocked at generic plugin route dispatch.
- The current plugin installation model is manifest-backed and explicitly registered at build time. It is not filesystem autodiscovery yet, but it gives the platform a durable admin-managed enablement layer for later drop-in plugin installation work.
- The unified Content tree uses a compact table/list layout rather than large cards.
- Course workspaces include a top-level Settings tab with an extensible left-hand subsection navigation built from the same shared `SettingsSectionNav` used by account settings. **General** owns existing-course subject, title, description, publication status, and the student content layout; **AI settings** owns the student-support AI agent selection. Student content layout is stored in course metadata as `studentContentLayout`, defaults to `accordion`, and also supports `folder_tabs`, where visible root folders use the shared left navigation and the selected folder's descendants retain expandable folder behavior. Loose root-level items remain available in a separate **Other content** block. Course creation continues to use the standalone `CourseForm` without exposing existing-course-only settings, while the legacy existing-course edit route redirects to Settings → General and the course hero has no separate Edit action. New course setting fields and categories should extend these subsections rather than recreate a separate edit page.
- Material and activity settings are edited from content-row controls in the unified tree.
- Course content activity rows can duplicate activities through an editable title dialog. The copy is an unassigned draft in the same folder with the same visibility; it preserves bank activity/version traceability and concept selections, copies plugin-owned course authoring through `onCourseActivityDuplicated`, and excludes the source `allGroupsAssignment` policy. Compound Tests use their dedicated deep-duplicate lifecycle and now place the duplicated shell in the same source folder too.
- Course Content duplication also covers plugin-backed GitHub, file, and text resources plus compatibility legacy materials. Copies remain in the same folder with the same visibility and use content-type-owned `duplicate` handlers. Current file copies share the immutable stored-file reference; all content plugins remove derived `embeddingIndex` metadata so copied resources rebuild indexes under their own identity.
- Folders support expand/collapse; student first-level folders render as accordions.
- Content moving uses pointer-based drag and drop with a drag handle, floating preview, target highlighting, a top-level drop zone, and an activation threshold so accidental handle clicks do not immediately move content.
- Branding uses the project logo from `docs/brand`.
- The app favicon uses the square Cognelo icon asset.
- The top header separates primary app navigation from personal controls.
- Dashboard is temporarily hidden. Login, first-time activation, the brand logo, `/`, and legacy `/dashboard` visits resolve through one role-aware landing rule: administrators, course managers, and teachers go to Subjects; students and other roles go to Courses.
- General account configuration lives under `/settings`, currently reached from the account menu. `/settings/profile` contains separate profile and password forms; password changes require the current password, use the shared notification/unsaved-change systems, and keep the authenticated session active.
- The sign-in form starts empty and never embeds seeded or production credentials. Its standard `username`, `current-password`, and `new-password` autocomplete semantics allow the browser or password manager to fill credentials only according to the user's saved-login preferences.
- The login submit button has an explicit non-native appearance and dedicated background across normal, hover, focus, active, and disabled states. Preserve this when restyling login: Safari autofill can otherwise repaint the background as transparent while leaving white button text, making the action appear to disappear.
- Production deployment is documented in `docs/DEPLOYMENT_UBUNTU_APACHE.md`. The reference topology uses two VPSs: the application host terminates TLS with Apache, runs separate systemd-managed web/API processes, PostgreSQL, background jobs, and durable per-instance uploads; the disposable sandbox host runs only Dockerized Judge0 and Playwright dependencies. A WireGuard point-to-point network gives the hosts instance-specific private addresses. Sandbox containers stay on an internal Docker network, while fixed-address systemd socket proxies expose only the selected host listeners; this preserves blocked container egress and avoids Docker Engine 29 dropping published ports for internal-only networks. The pinned Judge0 image runs as GID `999`, so its root-owned bind-mounted configuration is mode `0640` with group `999`, inside a protected runtime directory. The API starts after but does not `Require` WireGuard so non-sandbox Cognelo features remain available during a sandbox outage. An operator may explicitly accept authenticated plain HTTP over fixed public IPs and use UFW-restricted public socket listeners instead, and same-operator instances on one application host may intentionally share one sandbox stack after cross-version contract smoke tests; both exceptions share token, queue, upgrade, and failure domains. Start one approximately 40-student class with 4 vCPU/8 GB RAM on each host, load-test synchronized assessments, and scale the sandbox first when queues or Chromium failures appear. Isolated stacks remain the default for cohosted instances. `npm run production:bootstrap` initializes roles/plugin manifests/core activity types and the first administrator without development seed data.
- The current Cognelo production inventory intentionally cohosts two isolated application instances on one application/database VPS: `app1.cognelo.org` and `ets.cognelo.org` both run `cognelo-0.7.0`, as Unix accounts `app1` and `ets` on loopback port pairs `3100`/`3101` and `3200`/`3201`, with databases `cognelo_app1` and `cognelo_ets`, respectively. Each instance has its own `/srv/cognelo/INSTANCE/shared`, `.env`, storage directory, secrets, systemd services, Apache virtual host, and certificate. They share only the external Judge0/web-design sandbox service and its authentication token; no application files, storage, database, or Node process is shared. The sandbox host admits ports `2358` and `3456` only from the application VPS's fixed public IPv4, and the authenticated HTTP/firewall-only transport risk is explicitly accepted for this deployment.
- Production upgrades follow `docs/DEPLOYMENT_UPGRADE_UBUNTU_APACHE.md`. Every production GitHub Release must use `docs/RELEASE_NOTES_TEMPLATE.md` and provide an explicit upgrade section covering migrations, environment/manual steps, host/service changes, sandbox and all plugin-owned external dependency changes, plugin actions, post-upgrade jobs, smoke tests, and rollback. Each category says either exactly what to do or `None`; operators must not be expected to infer production actions from diffs or a hardcoded list of current plugins. Before a tag or release exists, the designated approver supplies a fresh current-production dump; the exact current commit is deployed to isolated pre-production, all core and plugin migrations and automated checks run against the restored clone, and the approver manually tests it. Only explicit approval permits creating a tag and GitHub Release, and that tag must resolve to the unchanged approved commit. Build against a temporary empty repository-level `storage/` directory, then restore and re-verify the instance's persistent storage symlink before migration: Turbopack traces the whole project for some server imports and otherwise aborts when an uploaded-file symlink resolves outside the deployment worktree. This build-only substitution must never modify or copy persistent storage. The consolidated migration script removes Prisma-only `schema`, `connection_limit`, and `pool_timeout` URL parameters before invoking `psql`, while preserving libpq parameters such as `sslmode`.

Monaco remains exactly `0.52.2` in `@cognelo/activity-ui`, with the same exact root dependency acting as the npm workspace peer-resolution anchor for `@monaco-editor/react`; removing that anchor can install a second newer Monaco copy with its own vulnerable DOMPurify dependency. The test toolchain uses Vitest `4.1.11` with Vite exactly `7.3.6`: allowing npm to select Vite 8 changes the TSX transformer to Rolldown/Oxc and currently makes the repository's `jsx: preserve` sources fail during test imports. Reassess these exact compatibility pins deliberately rather than broadening their ranges during an unrelated dependency refresh.

Subject, course general/AI, profile/password, core Test settings, MCQ, coding exercise, Parsons, web-design coding exercise, and Coding Homework Grader authoring use this convention.

## Internationalization Decisions

- The web app has built-in i18n with `en`, `fr`, and `zh`.
- Locale is stored client-side in `localStorage` and reflected on the document `lang` attribute.
- Visible platform UI copy is translated across login, navigation, dashboard, subject, activity-bank, course, material, and activity management UI.
- Plugin/activity definitions can provide localized `name`, `description`, and `defaultTitle` through the activity registry.
- The course detail page resolves plugin-localized activity labels from registry definitions instead of relying only on database display names.
- Activity bank lists and authoring pages also resolve plugin-localized activity labels from registry definitions instead of relying only on database display names.
- MCQ choices can include fenced code blocks, and MCQ activities can opt into randomized choice display without changing stable choice IDs used for scoring.
- Arabic (`ar`) is supported as a frontend locale. Selecting Arabic sets the document direction to RTL, and plugin activity metadata can provide Arabic `name`, `description`, and `defaultTitle` values.
- Platform-owned web translations are split by locale under `apps/web/src/lib/i18n/messages/*` and composed by `apps/web/src/lib/i18n/messages/index.ts`. Plugin-owned strings remain in the plugin package that owns the behavior or metadata, and platform locale files may compose plugin message bundles such as Parsons without moving those strings into core/web.
- Gradebook manual adjustment starts with a core teacher override workflow and a plugin-backed regrade workflow. Overrides update the current grade and write `overridden` grade events; automatic regrades resolve the plugin grading handler and record through the core grade service as `regraded` events. Parsons regrade evaluates the stored submitted attempt state against the current course-local activity config, so teacher corrections to an assigned course activity affect regrade results.
- Coding Homework Grader Phase 13 is implemented. Final challenge-answer submission for summative assigned activities creates/submits a core `ActivityAttempt` linked to the plugin submission; teachers review submissions from the activity gradebook detail page through the plugin manual grading renderer and save score/feedback with the existing core gradebook override workflow.
- Coding Homework Grader Phase 14 operational hardening is implemented around a shared core background job service. Core owns the durable `BackgroundJob` schema/service plus an API-started in-process worker; plugins register handlers by key. Student ZIP submissions support idempotency keys, enqueue grader processing jobs, append processing timeline metadata, categorize retryable/non-retryable failures, and the student view polls latest submission state until challenge questions are ready. Teachers can reprocess unfinished/failed submissions through the plugin route, which now enqueues the same shared background work. Centralized platform rate limiting remains a separate future policy.

## Known MVP Constraints

- File storage is local only for now; production should move to object storage while preserving the same course-material abstraction.
- Backend/server validation and error messages are not yet fully internationalized.
- Locale-prefixed routes are not implemented; localization is currently app-state driven on the frontend.
- Plugin registration is explicit, not autodiscovered. Installed plugins do have admin-managed enablement records, but adding a new plugin still requires build-time registry wiring.
- Judge0 dev infrastructure is local-Docker only; production still requires a separately managed Judge0 host with its own hardening, monitoring, and secrets management.
- Section/group pages remain student-facing in the same route tree. Teachers and administrators who open a legacy group URL are redirected to the matching Group perspective on the course Content tab, so student simplicity and manager consolidation still rely on explicit role-based routing rather than separate apps.
- Plugin registration is explicit, not autodiscovered. This includes server plugin hooks such as copying plugin-owned bank data into course activity copies; missing hook registration means plugin-owned bank data will not be copied.
