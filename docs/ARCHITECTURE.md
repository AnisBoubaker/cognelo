# Cognelo Architecture

Cognelo is a modular intelligent tutoring system for programming education.

## Stack Rationale

- **Next.js + TypeScript** for both API and web apps: one language, shared types, strong developer experience, and deployable apps without introducing microservices early.
- **PostgreSQL + Prisma** for relational integrity, explicit migrations, and future research-friendly querying.
- **JWT in HttpOnly cookies** for secure browser auth in the MVP, with authentication-version invalidation for administrator password resets and space for refresh tokens, SSO, and invitations later.
- **Zod contracts** shared between frontend and backend for DTO validation and stable API expectations.
- **Activity and content type registry packages** for plugin-style registration without coupling activity or non-activity content behavior to subjects, banks, courses, or the content tree.

## Production Topology

The production reference is a two-host deployment. The application VPS runs Apache/TLS, the Next.js web and API services, background jobs, PostgreSQL, and durable uploaded storage. A separate disposable sandbox VPS runs the privileged Judge0 stack and the authenticated Playwright command runner, with no Cognelo database credentials, JWT secret, application deploy key, or mounted application storage. Judge0 startup includes an idempotent, database-backed language-configuration job; workers start only after it has configured every active C and C++ runtime with the common system-library linker flags required by programming courses. Each production worker container uses a private cgroup namespace to keep cohosted instances’ sandbox IDs and accounting separate.

The reference hosts communicate through an instance-specific WireGuard point-to-point network. Judge0 and Playwright stay on an internal Docker network; fixed-address systemd socket proxies listen only on the sandbox WireGuard address, and firewall rules admit their ports only from the matching application peer. This preserves blocked container egress and avoids Docker Engine 29 silently discarding published ports for internal-only networks. The API systemd unit orders itself after WireGuard with `Wants` rather than `Requires`; a sandbox or tunnel outage may disable execution-backed activities but must not prevent the rest of Cognelo from starting. PostgreSQL remains loopback-only on the application host. The deployment runbook also describes a restricted forward-only SSH transport, an explicitly accepted fixed-public-IP firewall-only exception and a shared-stack exception for applications in one operator trust boundary. The complete operational procedure and initial capacity guidance live in `docs/DEPLOYMENT_UBUNTU_APACHE.md`.

## Monorepo Layout

```text
apps/
  api/                 Next.js backend API route handlers
  web/                 Next.js frontend application
packages/
  activity-sdk/        Activity type contract and registry
  content-type-sdk/    Content type plugin contracts and registry
  plugin-registry/     Installed-plugin composition root
  config/              Environment loading and validation
  contracts/           Shared DTO schemas and TypeScript types
  core/                Auth, authorization, subject, bank, course, material, activity services
  db/                  Core Prisma schema, migrations, Prisma client
  plugin-activities/   Activity plugin packages
  plugin-content-types/
                       Non-activity content type plugin packages
docs/
  ARCHITECTURE.md      Architecture memory for future sessions
```

The SDK packages contain contracts and mutable registries only; they do not import concrete plugins. `packages/plugin-registry` is the outer composition root that imports the installed plugin manifests/server modules and registers them. Every API route loads the server composition through the shared HTTP route bootstrap so mutable registrations live in the same compiled module graph as the route and core services that consume them; Next instrumentation separately loads it for startup/background-worker validation and is not treated as shared route state. The web renderer registries load their client composition, and seed/migration scripts load the narrow composition they require. `core`, `db`, both SDKs, shared contracts/UI/config, and activity plugins never depend on a concrete sibling plugin. `npm run architecture:check` verifies the package graph, protected source imports, plugin-to-plugin dependencies, API server imports, and absence of plugin-owned models from the current core Prisma schema; it runs before both the root test and build commands.

Shared cross-plugin frontend primitives live in `packages/activity-ui`. Its Tabler-backed `ActionIcon` registry supplies semantic icons to core and plugin actions; the web icon layer re-exports it as `AppIcon`. All ordinary buttons and action links use the global compact outlined CSS tokens. See [Action buttons and icons](ACTION_BUTTONS.md). In addition to editors, renderers, notifications, and unsaved-navigation guards, it owns the responsive `EditActionBar` used by guarded edit drafts, the portal-based `ContextMenu` used by row/action menus, and the blocking `ProgressDialog` used by long-running AI, runner, batch, import, synchronization, maintenance, and background-processing actions. `ProgressDialog` accepts either a real percentage or an honest indeterminate state, prevents dismissal and background keyboard interaction while running, and may expose a close action only after a terminal state. `MarkdownRenderer` is the sanitized platform rendering boundary for GitHub-flavored Markdown and KaTeX-compatible inline/display math, including `$$ ... $$`; authoring surfaces use the paired `RichTextEditor` instead of plugin-local textareas or WYSIWYG implementations. Shared code editors, code renderers, and Markdown code spans/fences opt out of browser translation, and editable code disables browser/extension writing assistance while ordinary prose remains translatable. The editor gives Visual and Markdown modes the same fixed-height, internally scrolling body; one accessible bottom drag handle resizes both modes, while the far-right mode-bar action opens the currently selected mode in a viewport-filling overlay without remounting its content. The editor renders formulas as protected, interactive KaTeX widgets in Visual mode and preserves original delimited Markdown through visual round trips. Its equation action and rendered equation widgets open a portal-based MathLive builder with inline/display placement, common structural shortcuts, and a mouse/touch virtual keyboard; MathLive remains a dialog-only dynamic import rather than part of ordinary editor or learner bundles. Complete delimited formulas entered or pasted as Visual text are preserved verbatim instead of being Markdown-escaped and become rendered widgets when Visual focus leaves. The editor's table action creates canonical GFM pipe tables from a size dialog; selecting a cell exposes contextual row/column insertion and removal actions while preserving the first row as the header. It does not offer cell merging because neither `colspan` nor `rowspan` has a portable GFM representation. Its image dialog uploads PNG, JPEG, GIF, or WebP through the core media API, requires alternative text, previews the upload, provides pixel/original-percentage/container-percentage width controls, and reopens from an existing Visual image for replacement, metadata editing, sizing, or removal. Sizing remains ordinary Markdown by encoding a private `cognelo-size` fragment in the image URI; the shared renderer alone converts that validated numeric metadata into a sanitized width style. `ContextMenu` renders outside clipping containers, flips and clamps to the viewport, and centralizes dismissal behavior; new contextual menus must use it instead of page-local absolute positioning. The action bar is presentational and receives the owning form's dirty, saving, save, and discard state; it does not merge persistence boundaries or infer whether unrelated immediate mutations are saved.

The API applies centralized Origin-based CSRF protection to unsafe browser requests, including anonymous authentication. JSON/multipart streams are bounded before parsing; oversized or overly nested data fails before schema work. Shared database-backed rate limits, encrypted model credentials, DNS-pinned personal-provider requests, and local credential generation are detailed in [Security boundaries](SECURITY_BOUNDARIES.md). Generic plugin dispatch is also an authorization boundary: course routes default to course-management permission but may declaratively request gradebook-read permission per method, bank authoring dispatchers require bank management, assigned group dispatch validates group assignment access, unsafe content-resource plugin methods require course management, and registrations without explicit supported type keys fail closed. Host dispatchers never identify concrete plugin paths.

A running progress dialog temporarily yields to shared confirmation prompts, allowing a teacher to accept or cancel a live edit. The shared `DialogProvider` queues promise-based confirmations and text prompts on the accessible `ConfirmationDialog`. Application and plugin UI use this layer instead of native browser modal APIs; only explicitly sandboxed learner-authored previews may expose those APIs.

The shared `useBodyScrollLock` coordinates progress dialogs, picker/filter overlays, and full-screen rich-text editors. Locks are counted per document body, support either cleanup order, and restore the original overflow only after the last owner closes. Components must use this hook rather than taking their own overflow snapshots, which can leave the page permanently unscrollable after overlapping dialogs close.

## Browser Test Architecture

Shared [code-editor undo ownership](EDITOR_UNDO.md) is separate from persisted answer state. A mounted Test attempt/view retains per-question/file Monaco models while plugin views remount; leaving or reloading discards those models. Restored answers are fresh baselines, and user edits/undo/redo use the existing serialized answer writes. No editor history is persisted.

The repository-level Playwright suite in `tests/e2e` exercises the web application against the real API and development database. Shared fixtures authenticate documented admin, teacher, and student accounts through the login API and create isolated browser contexts from the resulting HttpOnly-cookie storage state; the interactive sign-in and sign-out path remains independently covered through the UI. Stateful cross-role tests use one worker and provision uniquely named, availability-independent subjects, banks, courses, groups, assignments, and participants through authenticated public API routes so tests do not depend on durable seed dates. A shared scenario fixture can temporarily reassign the seed student as a group student, TA, or teacher, copies plugin-private bank authoring through the real course-copy lifecycle, and constructs ZIP uploads in memory. Teardown calls activity and bank deletion routes first so plugin-private lifecycle hooks run, then may use Prisma only for exact identifiers or unique generated values created by that test run, never broad prefixes or seed records. Browser actions favor accessibility roles, labels, and visible text, making the suite an additional check on usable semantics as well as behavior; stable direct selectors are reserved for editor inputs or rendered editor state that cannot be reached unambiguously through accessible names.

## Core Modules

- **Application time** owns the admin-only instance timezone, default-off permission for course overrides, and public server-time snapshot. Courses inherit the application zone until an explicit owner/admin saves a custom choice; an authorized course layout supplies the effective zone to nested pages and plugin UI. UTC instants stay unchanged; shared context formats dates and converts scheduling input. Clock synchronization uses monotonic elapsed time, while all access/deadline enforcement remains in server services. See [Application timezone and server time](APPLICATION_TIME.md).

- **Auth** owns password hashing, JWT creation, authentication-version checks, persistent account/source throttling, login/logout, forced-password-change gating, first-login email-verification gating, and current-user lookup. Session JWTs require issuer `cognelo`, audience `cognelo-session`, HS256, expiry, and authentication version; SEB token purposes cannot authenticate or renew sessions. Existing unscoped cookies require sign-in after this change. Browser JWTs and HttpOnly cookies retain an eight-hour lifetime, but each successful current-user check reissues both so an actively used workspace has a rolling session. The web client deduplicates interval/focus checks, preserves the current user object when the returned identity and authorization state are unchanged so mounted course data does not reload, preserves the authenticated user and mounted activity through transport or server failures, retries while showing a connection warning, and clears the user only after a confirmed unauthorized response. JWT validation errors, missing/inactive users, and authentication-version mismatches emit `auth_session_rejected` with a reason and, when available, a secret-keyed opaque session reference; tokens and email addresses are never logged. Database failures propagate as server errors rather than being misreported as invalid credentials. Password changes and administrative email changes invalidate older sessions; password changes renew the current browser cookie. Email verification locks the user row and binds code hashes to the current address. New self-activated accounts remain restricted to current-user, password-change, verification, and logout endpoints until their address is verified. The explicit assigned-password student-import path creates already-verified accounts with no forced password change so pseudonymous students can sign in immediately without email delivery. Six-digit verification codes expire after 10 minutes, have a 60-second resend cooldown and five-attempt limit, and are stored only as HMAC-SHA256 hashes.
- **Authorization** maps global roles, explicit course memberships, section participants, and activity-bank ownership into server-computed course capabilities consumed by both API services and the UI. Administrators are global. Explicit owners/teachers manage the course; only a global teacher owner or explicit course teacher grades course-wide. A pure course designer owner remains a designer, not a grader. Section teachers and TAs receive gradebook/challenge/export access only for assigned group IDs; section teachers additionally manage that roster, while neither section role releases grades or changes course structure/settings. Course-list/detail reads use the same scope and never treat `createdById` as authority. Section assignments maintain `section_derived` discoverability memberships without granting course-wide authority; explicit course-level TAs are unsupported. Removing the last matching section assignment removes derived access, explicit membership removal is effective on the next request, and the final explicit owner is protected. Staff/roster/settings changes append `CourseAuditEvent` records, while grade and feedback paths retain their own actor-attributed event streams. Grade and feedback review saves carry optimistic versions and return a conflict instead of silently overwriting another teacher.
- **Users/Roles** support many-to-many global roles and future additional roles. Admin-only user management lists and filters accounts, creates active accounts with initial passwords, edits identity plus global role assignments, displays verification status, explicitly confirms an unverified account without an emailed code, and issues temporary passwords to other users. Administrative confirmation sets `emailVerifiedAt` and deletes any outstanding verification challenge. A password reset increments `User.authVersion`, marks `mustChangePassword`, invalidates older JWTs, and restricts the next authenticated session to current-user/password endpoints until replacement. Changing an account email clears `emailVerifiedAt` and any outstanding challenge.
- **Email delivery** owns one global admin-managed sender and transport configuration. It supports vendor-neutral SMTP relay and Microsoft Graph app-only OAuth. SMTP passwords and Graph client secrets are AES-256-GCM encrypted in PostgreSQL with the instance-specific `EMAIL_CREDENTIALS_ENCRYPTION_KEY`; that key also protects email-verification code hashes, and public DTOs expose only secret-presence flags. The admin test path may target any valid address. Synthetic recipients, including `cognelo.local`, are captured in a private filesystem outbox before transport configuration is loaded; see [Email delivery](EMAIL_DELIVERY.md). The reusable system-mail path rejects recipients unless they are active users or unclaimed section participants awaiting activation; first-login verification uses it for active unverified accounts and renders the subject, text, HTML language, and direction from the requesting UI locale. Challenge submission automatically notifies active course-wide grading teachers and active teachers assigned to the challenged section through that guarded path, while teachers may optionally send a challenge answer to the student. Notification delivery is best-effort and never invalidates an already-saved challenge. Assigned-password CSV accounts are created verified and therefore never enter the verification-mail flow.
- **Execution runners** are admin-managed instance configuration under `/settings/runners`, not application endpoint environment variables. Judge0 jobs are queued and polled through core so only its worker needs execution privileges; the API container never runs synchronous jobs. Core persists Judge0, Web Design, and SageMath endpoints with optional AES-256-GCM encrypted request tokens, exposes only token-presence flags, and performs type-specific connection/capability tests. Multiple ordered rows per type are valid now; a single core resolver currently chooses the first enabled row so a future round-robin pool changes selection policy without changing plugins or persistence.
- **Maintenance** is an admin-only workspace under `/settings/maintenance` with its own reusable left-side subsection navigation. The Media section reads storage/reference metrics and the dry-run cleanup plan from core, then requires a danger confirmation before invoking destructive collection. Future instance-level operations such as automated release upgrades belong in additional Maintenance subsections, not in the general account Settings navigation or an unrelated plugin.
- **Subjects** own reusable curriculum context, a supported teaching-language locale used by subject AI generation, an optional default programming language for newly created Programming Exercises in their courses and banks, subject-level material, and a subject-scoped prerequisite knowledge graph. Concepts contain stable observable skills and stable misconceptions (specific wrong learner beliefs). Programming-language choices are derived from the runtimes exposed by the configured Judge0 instance; a Subject can instead declare multiple languages. Missing or multiple-language defaults leave each new exercise unconfigured until its author chooses a language. Manual graph deletions remain immediate, impact-analyzed operations. AI generation preserves retained stable identities and may attach an exact concept/skill/misconception deletion disclosure to the combined Subject draft; core transactionally retires only those disclosed omissions and removes their current bank/course activity mappings, while historical version snapshots remain immutable and all other omissions remain guarded.
- **Activity AI authoring** receives knowledge alignment through a host-owned shared context. Every generation mode receives the complete subject catalog of concepts, skills, and misconceptions as a curriculum boundary. Generators can additionally consume the live unsaved target draft, request catalog-constrained skill/misconception suggestions for their generated draft, or ignore the selection draft without reading or mutating it. The host keeps tab panels mounted and combines activity content with knowledge selections at the persistence boundary. Activity types with a dedicated grading authoring surface can opt into the host **Grading** tab after **Concepts**; Programming Exercises keep one mounted plugin state and portal their grading controls into that panel so tab navigation does not split the save boundary. Bank variation is a separate capability-driven path: core/background orchestration duplicates the complete independent draft first, preserves exact knowledge selections, supplies the catalog plus selected skills and misconceptions to `bankVariation.createVariation`, and reports durable per-child progress plus the final stored title. Handlers may return localized review warnings after saving a draft; the successful job result retains each warning with the affected copy ID and final title, and the host shows it in the completion dialog and shared notifications. Reusable Test variation invokes the same handler for every owned child and continues after warnings. Compensating deletion removes the copied graph on failure, retries plugin-private cleanup hooks three times, and surfaces incomplete cleanup distinctly.
- **Assessment feedback and AI grading** use a cross-plugin orchestration boundary. Course metadata holds a dedicated AI-feedback enablement switch and AI connection, separate from student support. Activity definitions advertise `supportsAiFeedback` and `supportsAiFeedbackGrading`; server plugins register an `aiFeedback.evaluateAttempt` handler returning an immutable feedback reference/version/hash, sanitized student feedback, and an optional grading result. Feedback-capable plugins also register `aiFeedback.teacherReview` submission, draft, and revision handlers plus an activity-definition renderer key. Direct AI-grading plugins register `aiFeedback.batchGrading` to read/update activity instructions and decide whether reviewed feedback is complete enough to serve as a consistency example. Before a whole-activity batch, the host offers up to three same-activity submitted/graded attempts whose grading content is complete, excludes them from reassessment, and sends only plugin-sanitized submissions/feedback—not learner identity—with the per-run instructions. Core revalidates every example at execution time; plugins snapshot effective instructions and example provenance privately. The detailed gradebook supplies one **Review and grade** surface with individual or whole-class navigation: the plugin renders the answer and validates editable narrative and rubric fields, while the host provides the audited final-grade override. Drafts may contain an activity's configured rubric even before automatic evaluation, allowing the same plugin-owned form and grading policy to support teacher-authored feedback. Programming Exercise rubric and assessment-feedback model prompts resolve the Subject teaching language server-side, not from the viewer's interface locale. Formative plugin routes call the evaluator immediately after an explicit learner check/submit. Summative submission only persists work; an authorized teacher invokes the direct attempt-evaluation endpoint from the gradebook, with no scheduled scan or background-job execution. Core records feedback-only results without changing deterministic grades, records plugin grading results through the normal grade lifecycle, and withholds all summative feedback until release. Learner-facing copy remains mechanism-neutral.
- **Feedback persistence and research** deliberately separate private AI artifacts and normalized learner-visible data. Each plugin stores complete request/rubric snapshots, provider response, parsed output, latency, hashes, score components, and failure details in plugin-owned tables; coding-exercise submission rows preserve the original private rubric/test result, while teacher-triggered corrections append new test or model evaluations using current authoring state. Feedback authored before grading is stored on `ActivityAttempt.metadata.teacherFeedback`, copied into a later grade unless that grading call supplies generated feedback, and recorded as `feedback_teacher_authored`. A later teacher edit updates that attempt copy plus the selected grade snapshot when present, preserves immutable model artifacts, records the previous/next snapshot in `GradeEvent`, and appends `feedback_teacher_revised` to `AiFeedbackResearchEvent`. A feedback plugin may return a grading result when an editable rubric score changes; core records it through the ordinary audited regrade service and appends `feedback_teacher_grade_adjusted`, while that review's deterministic component and configured weights remain fixed. Teachers may revise feedback after a challenge; the immutable generated artifact and challenge hash remain unchanged, while the linked grade/research events preserve the before/after teacher revision and challenge ID. Core also stores bounded append-only research envelopes for requests, completions/failures, grade recording, release/hide/view, Test parent recomputation, and challenge outcomes. The manager-only research route pseudonymizes participant/user/actor/attempt identifiers by default. It is an operational research extract, not yet a consent-aware production export; consent filtering plus retention/anonymization policy remain required hardening.
- **Grade challenges** are mechanism-neutral and opt-in per summative course activity. The setting is disabled by default, follows the General assignment policy, and can be overridden per section, prioritized team, or student. When the learner's effective assignment enables challenges, each released final grade tied to a submitted attempt receives an immutable challenge target, and separately identified generated or teacher-authored feedback may expose its own target. Disabling the setting prevents new challenges without deleting or hiding existing records. `GradeChallenge` preserves the released grade/feedback snapshot, required student explanation, response/status, optional resulting-grade snapshot, and plugin/Test-child identifiers. Students see their challenge beside the released answer. After the record is saved, core emails every active course-wide grading teacher plus active section teacher, de-duplicates users through a single authorized-recipient query, excludes the challenging learner, TAs, inactive accounts, and unrelated administrators, and records delivery counts in the research event; transport failure is logged without rolling back the challenge. The course-wide Challenges queue lists activity → student rows that reveal the explanation when expanded and opens the exact learner in the shared plugin **Review and grade** dialog without leaving the tab; the queue itself owns no grade editor. Open challenges are shown by default, while a **Show resolved challenges** checkbox reveals upheld/adjusted records after all open rows. Grade changes therefore continue through the normal append-only `GradeEvent` paths. Sending the required teacher response resolves the challenge as adjusted or upheld by comparing the current audited grade and challenged feedback with their released snapshots; an optional checkbox sends the response through guarded system email. Feedback-only AI such as MCQ explanations is not independently challengeable, but the released deterministic grade remains challengeable when the assignment enables challenges. Compound Test children retain distinct feedback targets even though the grade and release unit is the parent Test.
- **Activity banks** own reusable activity authoring and version history for a subject. `ActivityBankFolder` provides bank-scoped nested organization; folders and activities have a shared logical sibling order, while a dedicated activity-placement mutation keeps drag-and-drop changes outside the authored-content/version path. Reusable Tests are core bank activities with a normalized `BankTest` graph of hidden, independently owned child bank activities; each published shell version has an immutable ordered composition manifest referencing exact child versions. Bank/course Test transfer deep-copies the complete graph and invokes ordinary child lifecycle hooks, so deleting a source activity, bank Test, or bank never mutates existing copies. Folder deletion preserves top-level activities by moving every item in the deleted subtree to the bank root. The detail response derives per-concept activity counts from normalized top-level bank links, and the client applies inclusive concept filtering while retaining matching ancestor folders. Bank management is capability-gated (currently owner/admin), subject changes are allowed only while empty, and populated-bank deletion either transfers activities to a writable same-subject bank or cascades bank content after explicit confirmation while preserving detached course-local copies.
- **Bank activity lifecycle hooks** keep generic duplicate operations plugin-neutral. Core creates an independent unpublished draft with no version history, while activity plugins copy any private bank-owned authoring rows through `onBankActivityDuplicated`; its first publish creates version 1. AI variations deliberately start with this same deep copy so all private settings are independent before plugin-owned generation replaces the appropriate content. Moving retains the existing activity identity and therefore needs no plugin data migration.
- **Bank activity version comparison** is core-owned for immutable `ActivityVersion` data. A shared diff contract and `@cognelo/activity-ui` visualizer compare semantic core fields, knowledge selections, and recursive generic config/metadata paths. This gives every activity type a consistent fallback without plugin UI code. Private plugin authoring data remains outside historical comparison until it is version-snapshotted alongside each activity version.
- **Course activity duplication** creates an unassigned draft in the source content folder, preserves bank activity/version traceability and core concept selections, removes the source assignment-settings policy, and delegates private course-row copying to `onCourseActivityDuplicated`. Compound Tests use their dedicated deep-copy lifecycle while preserving the same-folder placement rule.
- **Course activity bank synchronization** reports in-sync, course-ahead, bank-ahead, or diverged state by comparing the linked course copy, its immutable imported version, and the latest published bank version. Retrieval updates the existing course and plugin-owned authoring data without changing placement or assignments, and is locked after any attempt. Publishing creates a new immutable version and delegates private course-to-bank replacement to `onCourseActivityPublishedToBank`; it remains available after attempts because it does not mutate the course copy or attempt snapshots. Bank writes require bank-management permission.
- **Content resource duplication** is content-type-owned through server `duplicate` handlers, allowing generic course content orchestration without interpreting file, repository, or text metadata. Core creates the copied resource and same-folder content placement only after the owning plugin returns safe copied metadata.
- **Courses** own course lifecycle, course-local material, and course-local copies of bank activities.
- **Course content resources** are plugin-backed non-activity resources such as GitHub repos, files, and text notes. Optional editor/viewer/presentation registry keys support dedicated authoring and inline, separate-page, or modal readers. Plugins declare Markdown fields for generic transactional media retention; section-scoped readers enforce membership and effective visibility. See the [Text material reference](../packages/plugin-content-types/plugin-text/docs/REFERENCE.md).
- **Course materials** are legacy generic records retained for compatibility while new non-activity content moves to content type plugins.
- **Student groupings** belong to one section and contain stable-ID teams. A student enrollment can join one team per grouping and be assigned differently in other groupings. Core owns membership validation, roster-scoped teacher authorization, revision-checked transactional saves, and actor-attributed audit snapshots. Staff management stays roster-scoped; enrolled learners use a separate names-only team projection and confirmation endpoint. Grouping visibility is independent of the persisted assignment method; hidden groupings are excluded from learner reads and confirmation lookups while retaining memberships. Per-team capacities, selection dates (exclusive Until), change permissions, and concurrent choices are enforced transactionally, with student choices advancing the teacher revision. See [Student groupings and teams](STUDENT_GROUPINGS.md) for API and lifecycle boundaries. Core-owned [activity exceptions](ACTIVITY_ASSIGNMENT_EXCEPTIONS.md) reference these stable team IDs, resolve current memberships, and apply General → section → prioritized teams → student policy per field without exposing private targets to learners.
- **Sections** are currently implemented by `CourseGroup` records and own participants plus activity availability windows. The course Participants tab manages all section rosters inline with modal group/participant forms. Its student CSV import is a client-side adapter over the existing single-participant mutation and accepts no header. Normal mode requires `first name,last name,email` plus an optional fourth `external ID`; assigned-password mode explicitly requires `first name,last name,email,password` plus an optional fifth `external ID`. It validates every email and the complete file before mutation, fixes the role to `student`, and never uploads the file itself. The assigned-password server mutation hashes the password, transactionally creates an active verified `User`, grants student access, and links matching pending participants. It may reuse an existing active, verified, unrestricted account only after the supplied password matches its hash; a mismatch fails without resetting credentials. Group deletion is transactional and cannot remove the final course group; participants can be deduplicated into another group, or permanently removed with their group-scoped gradebook records after explicit confirmation. Use "section" for these enrollment containers; student groupings and teams are separate concepts.
- **Activities** are typed course-local activity copies. Most delegate behavior to installed plugins; core-backed compound activities may use the same generic activity, assignment, content, attempt, and gradebook infrastructure without participating in plugin installation lifecycle.
- **Rich-text media** separates logical `MediaAsset` uploads from immutable `MediaBlob` bytes. SHA-256 content addressing deduplicates physical files under a two-level sharded local path, while field-keyed `MediaAssetReference` rows retain each Subject, bank draft, immutable bank version, course copy, Test revision, Test revision item, and content resource independently. The authenticated API authorizes delivery from those owners instead of exposing storage statically. Unsaved uploads remain staged for 24 hours; final-reference removal records an unreferenced timestamp, and garbage collection applies a 30-day grace period plus seven-day trash retention. Administrators inspect and run the same core collector through Maintenance → Media; deployments may schedule the CLI entry point as a systemd timer. See `docs/MEDIA_ASSETS.md`.
- **Standalone activity response drafts** persist bounded JSON state per assigned activity and student participant without starting or consuming a gradebook attempt. Interactive standalone renderers use a serialized state host, while plugins with richer draft models may retain their plugin-owned persistence. Final submission clears the generic draft on a best-effort basis. Compound Test children never use this table; they continue to autosave through `TestItemAttempt` under the parent Test attempt, and the Test shell remounts the embedded renderer at each item boundary so component/editor state remains scoped to that child.
- **Student code editing** uses the shared Monaco primitive from `@cognelo/activity-ui`. The web app's lifecycle hooks prepare the pinned Monaco distribution with the maintained DOMPurify module, failing closed if the vendor module boundary changes, in first-party public assets before development or production builds; the loader uses absolute, same-origin asset URLs so blob-backed language workers can fetch their modules, and never depends on a third-party CDN at runtime. A controlled textarea fallback preserves editable student state, including protected template prefix/suffix handling, when a restricted browser cannot initialize Monaco.
- **Safe Exam Browser access** is a shared assignment policy stored in `CourseGroupActivity.metadata.requireSafeExamBrowser` and allowed only when `assessmentMode` is `summative`. The ordinary-browser route exposes only a launcher summary, and the course overview does not probe guarded activity-scoped routes before the learner selects an assignment. Confirming launch closes the dialog and replaces the ordinary-browser route with section content; selecting the activity again obtains a fresh launch configuration. A generated, short-lived `.seb` configuration starts the exact assigned activity and has a deterministic server-calculated Config Key. SEB proves that URL-bound key through its request header or JavaScript API before the API creates a separate HttpOnly access JWT scoped to one user/course/group/activity. Shared assigned-activity API routes enforce that JWT before returning activity content or accepting draft, media, attempt, plugin, Test, or submission work; activity plugins do not implement their own SEB checks. Manager preview bypasses the student restriction. Student course responses select only activity identity/type fields, protected group assignments have authored content removed until the guarded detail endpoint succeeds, and full course-activity/group-assignment authoring services require course-management access.

## Content Model

The durable model is:

```text
Subject
  SubjectMaterial
  SubjectKnowledgeConcept
    SubjectKnowledgePrerequisite (requiring concept -> required concept)
  ActivityBank
    ActivityBankFolder tree
    BankActivity
      BankActivityKnowledgeConcept
      ActivityVersion
        ActivityVersionKnowledgeConcept
  Course
    CourseContentItem folder tree
    CourseContentResource
    CourseMaterial (legacy compatibility)
    Activity
      ActivityKnowledgeConcept
    Section/CourseGroup
      StudentGrouping
        StudentTeam
          StudentTeamMember (participant link)
      participants
      assigned activities and availability windows
```

`SubjectKnowledgeSkill` gives every observable skill a stable subject/concept-scoped identity, title, position, and active/retired state. `SubjectKnowledgeConcept.skills` remains a synchronized newline-delimited compatibility projection for older contracts and AI graph generation. Renaming or reordering a skill preserves its ID. Confirmed deletion retires the row, updates current mappings, and preserves immutable historical snapshots.

`SubjectKnowledgeMisconception` gives each wrong learner belief the same stable identity and lifecycle. `SubjectKnowledgeConcept.misconceptions` is a nullable JSON compatibility projection: legacy `NULL` reads as no misconceptions, while every graph save writes an explicit array, including `[]`. AI graph creation and iteration generate misconceptions and preserve exact retained IDs.

Bank activities are mutable drafts. Saving as Draft updates only the bank activity. Saving as Published creates a new immutable `ActivityVersion` when authored content differs from the latest published snapshot; publishing unchanged content reuses that version. Pausing or archiving is lifecycle-only and does not create a version. `currentVersionId` therefore represents the latest published version, even while newer draft edits exist.

Activity-to-concept links are a core, cross-plugin contract. All activity editors are host-wrapped with an Activity/Concepts tab set. Bank links are copied into immutable activity-version link rows and then into independent course-activity link rows during assignment; empty selections are valid, but no activity type may opt out of the capability.

Each bank, version, and course activity concept link stores `selectsAllSkills`, stable skill and misconception IDs, and their title snapshots. A whole-concept selection uses `selectsAllSkills = true` and includes every current target; an explicit selection of every target still uses `false`. Immutable activity versions snapshot concrete IDs/titles. Deleting a skill or misconception can replace it with another active item of the same kind in the concept or remove it from current bank/course activities; deleting a concept removes its current mappings. Historical activity-version snapshots are never rewritten. Attempts snapshot their resolved skill and misconception mappings at start.

When a bank activity is added to a course, Cognelo copies the selected/latest version into a course-local `Activity`. The course activity stores `bankActivityId` and `activityVersionId` for provenance, but the course activity is not live-linked to the bank. Course edits affect only the course copy; bank edits create future versions and do not alter existing course copies. Rich-text image references follow those same ownership boundaries without duplicating identical physical bytes.

Plugin-owned private data follows the same rule through server hooks. A plugin can copy its bank-owned reference data into course-owned plugin tables when a course activity is created from a bank version.

## Activity Extensibility

The opt-in [activity content closure policy](ACTIVITY_CONTENT_ACCESS.md) is core-owned. Current student limits/dates gate assigned routes, plugin histories, compound children, grade-report projections, and media delivery. The host replaces closed activities with receipts and released totals; declared finalization routes can complete expired work without returning question/answer payloads. Plugins retain private data and ordinary grading ownership.

The group **Student view** reuses the exact learner course-content component plus learner activity renderers through a separate, fail-closed renderer registry and execution adapter. Every activity definition must declare `interactive`, `read_only`, or `unsupported`; interactive types require the matching client adapter and, for plugin execution, exactly one stateless server registration. Core resolves content and assigned activities with forced learner visibility/availability even for a manager. Temporary answers remain in `sessionStorage`; runner-backed preview actions use the dedicated `ServerActivityPlugin.studentPreview` contract and `/student-preview` routes. The shared browser API client blocks ordinary mutations from Student view as defense in depth. The outer composition root registers or replaces plugins by stable key, which keeps development hot reload current; complete cross-registry validation runs in production startup and plugin-registry integration tests rather than against transient development graphs. This is deliberately separate from ordinary plugin routes and from compound-Test persistence so preview requests cannot create academic records. See [Student view](STUDENT_VIEW_IMPLEMENTATION_PLAN.md).

Activity contracts and provider metadata live in `packages/activity-sdk`; installed plugin definitions are registered by `packages/plugin-registry`. Plugin-backed types resolve to an installed activity plugin under `packages/plugin-activities/*`; core-backed types use core services/renderers and do not have plugin installation, activation, backup, or dispatch behavior. Core services store bank activities, activity versions, and course-local activity copies, validate common state, and keep generic `config` and `metadata` as JSON. Authored config is not a transport DTO: learner routes use `ActivityDefinition.studentConfig` (empty when absent), omit generic authoring metadata and nested bank/version rows, and project historical Test children too. Grading retains the original server records. The shared activity description is the student prompt and allows up to 30,000 characters for passage-based activities.

The first core-backed definition is `test`. A Test is a compound summative activity whose normalized `TestItem` rows own ordinary plugin-backed child activities. Its dedicated course authoring action is available while the type stays disabled in the generic plugin activity list; child activities are hidden from ordinary course and assignment lists. The outer Test Activity is the only assignable/content/gradebook unit. Manual Test submission opens an answer-status review from the last exercise, then requires a final grading confirmation; plugin-owned response checks are registered by the web composition layer and never evaluate correctness. The implementation sequence and runtime contract live in `docs/TEST_COMPOUND_ACTIVITY_IMPLEMENTATION_PLAN.md`.

Teacher Test regrading reruns all submitted manifest children through the composite execution boundary, using an optional plugin `regrade` handler for immutable evidence and rubric composition. Its authenticated POST streams measured progress to the shared dialog; whole-class regrading uses the same per-attempt batch. Child results are audited independently, while the parent total changes only after a complete batch. AI/manual grading retains a separate aggregate-only operation. See [Test regrading](TEST_COMPOUND_ACTIVITY_IMPLEMENTATION_PLAN.md#teacher-automatic-regrading).

Composite submission and regrading return an optional opaque `pluginAttemptRef` independently of the grade; core persists it even for submitted-ungraded work. The owning plugin validates and resolves legacy submission evidence without core interpreting private state or rewriting historical answers.

Test teacher review composes the existing standalone plugin feedback forms and server handlers with an authorized child context. Core owns numbered navigation, item overrides, optimistic versions, and the transaction joining child review/audit with aggregate-only parent grading. Partial review does not grade unfinished siblings. See [Test teacher review](TEST_COMPOUND_ACTIVITY_IMPLEMENTATION_PLAN.md#teacher-review-and-grading).

Course authoring remains live while attempts are unsubmitted. Core coordinates parent-Test locks, confirmation/messages, public audit, soft removal, and final submission revisions; plugins own private authoring revisions and pure response-reconciliation/student-state projection hooks. Summative result APIs enforce core release visibility, and a composite handler may return a null grading result for submitted work awaiting grading. See [Live activity authoring](LIVE_ACTIVITY_AUTHORING.md).

To add a new plugin-backed activity type:

1. Add or import an `ActivityDefinition`.
2. Add it to the client and, when applicable, server arrays in `packages/plugin-registry`.
3. Optionally add type-specific config validation.
4. Add frontend renderer/editor components keyed by `activity.activityType.key`.
5. If the plugin has private bank-owned data, add a server plugin hook to copy that data when a bank version becomes a course activity.

Plugins whose released learner report needs activity-specific evidence may also register a server-side `studentGradeReport` handler. The generic Grades route invokes it only for final released rows; the plugin must recheck learner ownership and release state and return a bounded student-safe projection rather than private grading records.

Solution-capable definitions opt into `supportsSolution`, with a type-scoped `studentSolution` server handler that returns only displayable Markdown/code. Core owns the default-off course setting, learner enrollment/access checks, summative grade-release gate, and compound Test aggregation. The host requests private reference content only after an explicit reveal; the ordinary answer renderer stays mounted while the solution tab is open. See [Student solutions](ACTIVITY_SOLUTIONS.md).

Plugins whose final grade has multiple independently completed components register a batch `gradeCompletion` handler. The teacher gradebook combines that plugin-owned classification with core attempt state: submitted-ungraded or partial rows prevent release, explicit teacher overrides are complete, and learners without a submission never block the item.

The course workspace loads heavyweight tab data independently. Its Content tree has an explicit loading state and is not gated by gradebook retrieval. For an authorized grader, a staff Content-tree activity link opens the same detailed activity-report workspace as the Gradebook, defaulting to the inline Class overview; a persistent permission-gated editor link keeps authoring one action away. Designers without gradebook access retain the editor destination, and section links open that same report workspace with a section filter for course managers. Legacy assigned URLs redirect managers to the report; learners remain on their assigned route. The report header also exposes the same manager-only assignment-settings modal used by course content. The course Gradebook overview requests a server-computed summary containing only course/activity/group aggregates; learner identities, row details, and attempt histories are fetched only by detailed result surfaces or exports. The detailed **Student results** tab polls a separate authorization-scoped activity/group feed containing only current-mode in-progress attempt identities, numbers, and start times; it never polls the full detailed gradebook response. Each result row exposes its capability-driven grading and inspection actions through the shared three-dot `ContextMenu`, while whole-activity batch actions remain visible above the table. The per-student review dialog resolves the newest submitted/graded core attempt in the assignment's current mode and loads its plugin payload first; exact older plugin/Test payloads are fetched only when navigated to, and historical/formative views are read-only.

Attempt creation takes a transaction-scoped database lock per gradebook item and participant before rechecking resumable work, counting allowance, and allocating the next number. Every standalone learner check/submission that represents an inspectable attempt writes a core `ActivityAttempt` in addition to any richer plugin-owned record. Course assignment metadata offers `formative`, `formative_ai`, and `summative`; the first two both map to the stable `ActivityAttempt.assessmentMode="formative"`, while `formative_ai` alone authorizes a capable plugin to generate and expose attempt-specific automatic feedback. Summative limits, grade selection, grading, and release queries ignore formative attempts. Changing either formative policy to summative does not rewrite history, so old practice attempts remain inspectable but cannot pollute the summative report or grade. Changing summative to either formative policy is a data conversion: the API requires explicit confirmation, converts existing assignment attempts to formative, deactivates the current grade snapshots, clears release, and appends `assessment_mode_changed` events for every student. The grade rows remain as inactive historical snapshots so the append-only event trail and prior grade evidence are retained.

The shared result-row menu can also soft-delete any submitted/graded attempt in the assignment’s current assessment mode through a plugin-independent selector with a mandatory teacher reason. The existing deletion endpoint retains attempt/child records, records the audit, recomputes active grades, and invokes retained-record plugin hooks. Learner deletion history includes the record and reason but omits raw grade snapshots. The host renders learner code/files from retained submission metadata, including existing deleted records. History-capable renderers expose prior submissions before the start gate; history inspection never initializes an answering attempt or draft. See [submission deletion](GRADEBOOK_IMPLEMENTATION_PLAN.md#submission-deletion).

The shared result-row menu can reopen the learner's latest completed attempt. Core preserves attempt identity, original timing, and authored snapshots while atomically restoring response state, reopening compound children, withdrawing/recomputing the grade, and appending the original submission evidence to `GradeEvent`. Plugins restore their own state through explicit `attemptContinuation` handlers using the host transaction; generic core code never queries plugin tables. Reopened work uses current effective assignment policy, including extensions and individual exceptions added after submission. See [Submission continuation](SUBMISSION_CONTINUATION.md).

Timing is a core course-assignment policy, not an activity-type feature. General settings may enable a 1–1440 minute limit for any formative or summative activity, and each group can inherit, replace, or disable it. The explicit learner start creates the ordinary core attempt immediately. Unsubmitted standalone and compound attempts use the latest effective limit from General, section, team, and student policy; deadlines use the original start and are capped by the effective assignment Until date. Countdown, write guards, and timeout finalization share that calculation after exception resolution. Submission records `submittedTimeLimitMinutes` and `submittedAvailableUntil` separately, preserving the original limit/manifest and leaving submitted history stable; older submissions without the Until snapshot retain their duration-based timing. The learner host refreshes policy every 20 seconds without replacing drafts. Settings mutations require confirmation when answering presence exists and can persist an optional in-app broadcast in the same transaction; see [live assignment policy](ACTIVITY_ASSIGNMENT_EXCEPTIONS.md#live-updates-and-teacher-notices). Assigned plugin dispatch and standalone draft saves reject timed learner writes before start and after expiry, while declared final-submission methods may finish the already-started attempt at zero. The web host supplies a generic countdown and `TimedActivityAutoSubmit` signal to the registered renderer; the plugin invokes its existing final submission so private artifacts and grading remain plugin-owned. If it cannot finalize incomplete work, core submits the timed attempt ungraded and retains any core response draft in the timeout metadata. Compound Tests use the same course policy but keep their dedicated parent-attempt manifest and finalization runtime. Countdowns advance from server-reported remaining seconds with a monotonic browser clock. Authorized teacher results/gradebook reads perform transactional [Test timeout recovery](TEST_COMPOUND_ACTIVITY_IMPLEMENTATION_PLAN.md#timeout-recovery) for disconnected or interrupted expired attempts, preserving responses as submitted-ungraded work with an audit event; no scheduled recovery worker is required.

Activity messaging is core-owned and plugin-independent. Activity-wide, default-off messaging and two-way switches control broadcasts and student-initiated private replies. `ActivityConversation` preserves assignment/enrollment/attempt identity; the host combines retained records in paginated activity chat and offers attempt-filtered discussion in shared submission review. Explicit broadcasts fan out to all enrolled students in authorized sections, including offline students, without creating academic attempts or answering presence. Recent presence remains a separate concern for live-settings warnings and optional notices. Teacher messaging permissions, grading-staff read access, student ownership, and activity content closure are enforced by core and the assigned-route guard. Author-only soft deletion preserves message text and timestamps, atomically marks broadcast copies, and invalidates the existing lightweight messaging revision. The shared timer/envelope and chat UI live in the host, so activity renderers remain unaware of messaging. The core Test host publishes its selected item in memory; message sends validate that item against the active attempt and preserve a title/number snapshot using the shared live-Test ordering helper. The existing teacher status poll carries scoped unread/sender metadata for visible alerts and local Web Audio chimes without fetching bodies or adding a timer; sound preferences remain browser-local. See [Activity messaging](ACTIVITY_MESSAGING.md).

No course table rewrite is required.

Teacher [answer exports](ANSWER_EXPORTS.md) use the capability-driven `submissionExport` server contract. Core authorizes and selects exact submitted attempts, plugins return their own safe document blocks, and the API prints escaped HTML with scripts/network disabled in a separate local Chromium context. PDF/ZIP generation is read-only and independent of the untrusted-code execution runners.

## Content Type Extensibility

Content type plugins are the sibling system for non-activity course content. Their contracts/registry API live in `packages/content-type-sdk`, their installed composition lives in `packages/plugin-registry`, and implementations live under `packages/plugin-content-types/*`.

Content create/update/duplicate results may return an `afterPersist` callback. The host invokes it after writing the public row, within the same database transaction, supplying only neutral tagged-template query/execute methods. This lets plugins save or copy private records atomically without adding private fields to generic resource metadata or concrete table knowledge to core.

Core owns:

- `CourseContentItem` for folder placement, ordering, nesting, and visibility
- `CourseContentResource` for the generic resource row
- `ContentTypePluginInstallation` and `ContentTypePluginTableBackup` for activation, enablement, and backup state
- generic course/group content resource API routes and plugin dispatch

Effective content visibility is also an authorization input. A group may override the visibility of any inherited course content item without mutating the course default; group-specific placements retain their stored visibility and ordering. When a group assignment shadows an inherited course activity placement, core returns the inherited placement with the selected assignment identity merged into it, so visibility, folder placement, ordering, and actions never come from conflicting rows. Learner course-level content/resource/material reads combine only authorized section views; caller visibility flags cannot relax filtering, and section endpoints require actual membership. Student content listings omit hidden items and descendants of hidden folders, and non-manager assigned-activity resolution applies the same rule before serving the activity or dispatching any activity plugin route. Teachers manage structure in Course perspective and use Group perspective only to inspect effective content and override visibility; separate group workspaces remain student-facing.

Content type plugins own:

- picker metadata, localized labels, semantic icon names rendered by the web app's centralized Tabler icon layer, and default titles
- create/update/delete validation
- settings and viewer components registered by renderer key
- plugin routes such as file upload/download
- storage details and plugin-owned tables when generic metadata is not enough
- `getEmbeddingSource` handlers for future indexing

Content definitions may declare a `presentationRendererKey` for a frontend registry resolver that projects safe href, target, and plain-text description from plugin-owned metadata. Settings adapters receive generic metadata state/change callbacks for plugin-owned fields. This keeps link-specific interpretation in the plugin and composition registry rather than course pages or core services; `ContentTypeOpenAction.target` supplies the equivalent server navigation hint.

Enabled content type plugins can be selected for new content resources. Active but disabled plugins can still serve existing resources. Inactive or unavailable plugins are blocked at dispatch and existing content rows render as unavailable.

The current content type plugins are:

- `packages/plugin-content-types/plugin-github-repo`
- `packages/plugin-content-types/plugin-file`
- `packages/plugin-content-types/plugin-text`
- `packages/plugin-content-types/plugin-link`

Embedding readiness is deliberately generic. Core exposes `getContentResourceEmbeddingSource`, which dispatches to the owning content type plugin and returns one of:

```ts
type ContentEmbeddingSource =
  | { kind: "text"; text: string; sourceId: string }
  | { kind: "file"; fileRef: string; mimeType?: string; sourceId: string }
  | { kind: "external_url"; url: string; sourceId: string }
  | { kind: "none"; sourceId: string };
```

There is no embeddings/index database yet. Future activity generation should ask a generic indexing service for relevant course context; it should not import concrete content type plugins directly.
