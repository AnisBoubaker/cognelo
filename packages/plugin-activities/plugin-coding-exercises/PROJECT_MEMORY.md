# Programming Exercises Memory

Read [docs/DECISIONS.md](docs/DECISIONS.md) only for the area being changed.

- The [student solution contract](../../../docs/ACTIVITY_SOLUTIONS.md) is capability-driven and default-off. Core gates explicit reveals by current assignment access and the summative grade release; the plugin returns only displayable reference content, never grading internals.

- No enabled hidden tests must not block submission or manufacture a grade. Private live edits are audited in plugin revisions, and summative execution/history outcomes are release-gated on the server. See [the reference](docs/REFERENCE.md#live-authoring-and-grade-visibility).

- The compound Test answer-review check must inspect response presence only, never correctness or grading evidence; automatically persisted initial state is not a new answer. See [the reference](docs/REFERENCE.md) for this plugin’s criteria.

- Public activity config is student-visible. Reference solutions, full templates, hidden tests, rubrics, and raw evaluation artifacts must remain private.
- Judge0 is server-only and all source/input/output fields cross its boundary as Base64. Status 13 is an infrastructure failure, never a learner result or consumed attempt.
- Judge0 endpoint, auth header/token, enablement, and per-process/thread flag are admin-managed core runner settings. Plugins must resolve the service through core rather than read runner environment variables; core currently selects the first enabled runner and preserves the boundary for later round-robin pools.
- Bank/course private rows require copy, sync, duplication, and deletion hooks. Reusable bank Tests must invoke those hooks per independently owned child rather than referencing a source bank activity. Duplication must copy the complete private configuration; generated reference solutions must merge rather than erase rubrics.
- Bank variation starts from an independent deep copy, preserves exact knowledge selections and rubric/config, and regenerates the prompt, metadata, reference/template, and tests. Require a substantive reasoning change, not renaming or a new story: independently review complete source/candidate context for novelty, alignment, and consistency before generating tests; retry rejected prompt/solution pairs up to three times, then fail for graph cleanup. Testability replacements must pass the same review. Original test counts are targets: keep validated subsets, or a test-free reviewed draft after recoverable test-generation failures, and return localized review warnings. Never retain copied source tests or mix solution candidates' tests. Ordinary save validation remains mandatory; variation alone may prune non-passing cases and revalidate. Unrelated failures still throw for whole-graph cleanup. See [Authoring UX](docs/REFERENCE.md#authoring-ux).
- Enabled hidden tests must pass the private reference solution before save. Persist per-test validation fingerprints, reuse only matching passing results, and rerun new, execution-relevant changed, or previously failing tests; reference solution, language, time limit, or private template changes invalidate every test. The signed preflight receipt prevents the persistence request from executing the same dirty tests again. `{{ STUDENT_CODE }}` is required; `{{ TEST_CODE }}` is the optional per-test harness insertion point.
- AI test generation offers Add (default) or Replace, with 0–15 new tests per kind and a positive total. Add preserves existing cases and sends their full current draft contents to every model attempt for complementary coverage; reject exact input/harness repeats across kinds. Replace clears a kind when its count is zero. Give new cases fresh IDs and respect total limits of 15 visible/50 hidden tests. Validate cases independently, retain passing cases and fingerprints across retries, and return partial authoring results with a count warning. Generation alone may collect per-case execution failures; saves and learner grading still fail closed, while bank variations may complete with review warnings. Generated tests use unordered `contains_lines`, non-empty expected output, and descriptive names capped at 50 characters; callable harnesses must print the expected result. See [Authoring UX](docs/REFERENCE.md#authoring-ux) for request context, validation summaries, and retry rules.
- Standalone drafts use core `ActivityResponseDraft`; embedded Test drafts use `TestItemAttempt`. Do not mix those persistence paths. Inspecting previous submissions must not initialize an empty draft before the timed start. Preserve `submittedSourceCode` in core metadata; normal history filters deleted core references while deleted history renders that retained source.
- Standalone time limits are core course-assignment policy. Practice runs/draft writes stop at the core deadline, and `TimedActivityAutoSubmit` must invoke the ordinary hidden-test submission so the already-started timed core attempt receives the plugin execution reference and result. Until submission, core refreshes the effective deadline from the original start; keep response state intact during policy refresh. Core resolves [team/student exceptions](../../../docs/ACTIVITY_ASSIGNMENT_EXCEPTIONS.md); reuse its effective context and grading services rather than querying team policy inside the plugin.
- The definition declares `studentView: { mode: "interactive", execution: "plugin" }`. Teacher Student view uses a third, browser-scoped state path; Judge0 preview runs/submissions are stateless and must never create plugin executions, snapshots, core attempts, grades, or analytics rows.
- Every successful standalone submission uses a mode-tagged core attempt. Only summative attempts consume attempt limits or enter grading; unclassified legacy plugin submissions remain inspectable but do not consume a summative attempt. Practice-run grouping is derived from timestamps around submissions. The current-run panel shows the newest run first and reveals older runs only on request; a new latest run resets that disclosure. Do not trim persisted history or alter previous-submission grouping to implement this presentation.
- Judge0 output is compared before truncation. Bound new execution/validation diagnostics when saving and bound legacy rows again when serializing them, or one runaway run can stall every later history view. Learner execution text must also wrap unbroken lines inside shrinkable containers so output cannot widen the editor/test workspace.
- Course-manager visits through assigned section URLs enter the shared activity-report workspace; its Edit action opens the canonical editor shell. Never mount a bare plugin authoring form on the learner route: it omits Concepts and falls back to inline grading. The host owns the tabs, grading portal, and assignment-settings modal.
- Rubrics are general teacher grading tools, not conditional on model feedback. Summative model grading is teacher-triggered. Formative model feedback runs only for the explicit `formative_ai` course-assignment policy; ordinary formative work never invokes or exposes it.
- Whole-activity AI grading uses the shared guided-batch contract. Candidates must already be graded and contain criterion explanations plus at least one narrative comment; at most three may be selected, selected examples are excluded from reassessment, and learner identity is never included in the model payload. The run uses the dialog instructions whether or not the default-on setting update is kept; persistence updates only the current course activity's private instructions once before the batch.
- Teacher review and AI-grading routes consume core course capabilities: explicit course teachers/admins work course-wide, while section teachers/TAs are restricted to their assigned groups. Hidden-test mutation, authoring, release, and persisted activity-wide AI-instruction changes remain course-management operations.
- Submission deletion uses the shared core row action with a mandatory reason. Retain execution/source records; the core deleted lifecycle excludes the submission from active grading while student deletion history keeps its reason. See [gradebook deletion](../../../docs/GRADEBOOK_IMPLEMENTATION_PLAN.md#submission-deletion).
- Original executions and submission-time snapshots remain immutable. Teacher test regrades append private test-evaluation records; teacher-triggered feedback uses the current rubric and latest successful test run, whereas formative/Test-child evaluation retains the submission snapshot. Final grade recomposition uses current component weights and core audited regrade flows; a missing rubric score never counts as zero.
- With rubric grading enabled, a deterministic tests-only score is a partial grade until rubric evidence exists or a teacher records a final override. The plugin reports current component completeness to the gradebook; partial and submitted-ungraded rows block release, while true non-submissions do not.
- Gradebook **Review and grade** combines the submitted code, latest test evidence, rubric scores, Summary/Strengths/Improvements, and the host final-grade override. It shows the automatic-tests and rubric contributions against their configured proportions plus their live calculated total. Its confirmed clear-content action empties only learner-facing narrative and criterion explanations in the unsaved draft; it preserves rubric/test scores and the final grade. Rubric edits recompose first; an explicitly changed or previously teacher-set final grade is then recorded as a separate teacher override. Released final grades and generated or teacher-authored feedback can be challenged only when the effective summative assignment setting permits it; the course Challenges tab mounts this same dialog in place. Challenged feedback remains editable because core retains the immutable artifact/snapshot and challenged hash while linking every teacher revision and grade change to append-only audit/research events.
- The shared attempt-review dialog loads the newest current-mode core attempt first. It requests older submission feedback/evidence only when the teacher navigates and renders older or formative attempts read-only. Programming formative inspection uses plugin execution evidence directly rather than the core regrade review endpoint, and includes the latest immutable feedback linked to that exact execution.
- Gradebook **Class overview** combines the private reference solution and hidden-test aggregates with the configured rubric. Each rubric criterion remains visible when ungraded. Aggregation prefers current gradebook feedback so teacher-authored and revised summative scores win, then falls back to the matching attempt's completed evaluation for formative work that has no grade.
- The released learner grading report is plugin-owned and release-gated. It includes all active submitted/graded code attempts and their latest saved test evaluations, sanitized teacher comments/rubric explanations, conditional automatic-test/rubric contributions, and the final total; it must not expose hidden inputs, expected outputs, private rubric instructions, reference solutions, or raw model artifacts.
- Rubric and learner feedback generation use the Subject teaching language, not the viewer locale.
- New course and bank exercises, including local Test children, inherit the optional single-language Subject default selected from the configured Judge0 runtimes. Missing and multiple-language Subject values deliberately create an exercise with no language; saving, generation, validation, and execution are blocked until the author chooses one. Existing and copied exercises retain their saved language.
- Monaco assets use the shared absolute, first-party URL configuration for blob-worker loading and SEB compatibility, with the controlled plain-text fallback retained.
- The student template projection drops whitespace-only hidden boundaries. Monaco cursor and selection limits must be derived from the current model rather than the previous React value so empty answers accept their first keystroke and select-all clears only student code.
- Monaco/basic code editors, rendered code, and Markdown code spans/fences inherit the shared non-translation policy; never extend that opt-out to the surrounding instructional prose.

- [Submission continuation](../../../docs/SUBMISSION_CONTINUATION.md): Restores source code from the exact learner-owned execution to the core response draft without changing the immutable execution. The next ordinary submission creates fresh execution evidence on the same core attempt. Restore through the host transaction; reopening preserves the original start and applies current exceptions.

- [Compound Test timeout recovery](../../../docs/TEST_COMPOUND_ACTIVITY_IMPLEMENTATION_PLAN.md#timeout-recovery) preserves the saved response without a plugin execution or invented grade. Later teacher-triggered [Test regrading](../../../docs/TEST_COMPOUND_ACTIVITY_IMPLEMENTATION_PLAN.md#teacher-automatic-regrading) evaluates every child, including already-graded children, while preserving timing, audit evidence, and grade-release gates. AI/manual grade aggregation must not trigger automatic reruns.

- Display timestamps through the shared application-time context (the effective course zone within course pages) and explicit-zone formatters; the browser timezone is not a user preference. See [Application time](../../../docs/APPLICATION_TIME.md).

- Honor the host [activity content closure policy](../../../docs/ACTIVITY_CONTENT_ACCESS.md) for prompts, histories, solutions, and files. Final submission may return a host-handled closure signal instead of a review payload; preserve records and finalization cleanup.

- [Undo and autosave](../../../docs/EDITOR_UNDO.md): wait for successful draft loading before mounting the editor. Restoration is a baseline, not an undoable edit or an answer write. Keep model history in its mounted attempt/question/file scope only; never persist history or let it cross attempts, users, files, or read-only submission views.

- Reuse `ActionIcon` from `@cognelo/activity-ui` and the shared [action-button rules](../../../docs/ACTION_BUTTONS.md); keep localized labels and action semantics, without plugin-local SVG/emoji substitutes.
