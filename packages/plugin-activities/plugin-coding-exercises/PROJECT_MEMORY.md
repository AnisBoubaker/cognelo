# Coding Exercises Plugin Memory

This file is for coding-exercises-specific memory only.

## Long-Term Plugin Decisions

- Use Judge0 as a remote execution backend instead of running untrusted student code inside the Cognelo API app.
- Keep Judge0 behind Cognelo server routes; never expose Judge0 credentials or direct Judge0 browser calls.
- Always call Judge0 submissions with `base64_encoded=true`: UTF-8 encode `source_code`, `stdin`, and `expected_output`, then decode `stdout`, `stderr`, `compile_output`, and `message` before comparison or persistence. Judge0 can otherwise return an HTTP-success error payload with no execution fields when source text contains accented or other non-ASCII characters.
- Treat `Activity.config` as student-visible and keep hidden tests plus grading internals out of it.
- In development, run Judge0 locally with Docker Compose. The default image is the pinned Apple Silicon build `ghcr.io/anisboubaker/judge0-arm64:1.13.1-dev.2`; `JUDGE0_IMAGE` is the override boundary for other architectures or approved builds. Docker Desktop uses Judge0's per-process/thread time and memory fallback because it does not delegate a usable cgroup-v2 subtree; this is trusted-development compatibility, not production-equivalent isolation. Development also uses `COUNT=2` to prevent the host CPU count from creating an excessive isolate worker pool. Both Judge0 containers must mount `infra/judge0/isolate.dev.conf`: Isolate 2.x otherwise allows only box IDs 0-999 while Judge0 derives the box ID from its ever-increasing submission ID, causing every later execution to fail before writing `/box/<source file>`. Its advertised C, C++, Go, Java, JavaScript, Python, Rust, and TypeScript runtimes must remain backed by real compile/execute smoke tests, and the exact-name allowlist in `coding-exercises.ts` must be updated whenever the pinned image's runtime patch versions change.
- Keep per-submission compiler options disabled. The infrastructure-owned, idempotent `infra/judge0/configure-languages.sql` adds `-pthread -lm -ldl -lrt` to every active C and C++ compile command, and Compose must complete that one-shot configuration before workers start. These flags cover the standard course-level POSIX/math system libraries; language standard libraries are already linked by their compiler drivers, and optional third-party libraries are not guaranteed. Initial deployment and upgrades must copy the SQL with the Compose template, explicitly rerun it when its contents change, and validate a real C `sqrt()` submission.
- In production, point Cognelo to a separately hosted Judge0 server through environment configuration.
- Hidden tests live in `PluginCodingExerciseHiddenTest`.
- Teacher reference solutions live in `PluginCodingExerciseReferenceSolution`.
- Practice runs and later submissions live in `PluginCodingExerciseExecution`.
- The first execution route is `coding-exercises/run`, which stores each run server-side before and after the Judge0 request.
- Hidden tests are managed through the teacher-only `coding-exercises/hidden-tests` route.
- Bank activity authoring now has bank-owned private coding test/reference tables; course assignment must copy those private records into course-owned plugin tables via `onCourseActivityCreatedFromBankVersion` so coding exercises persist the same authoring data in banks and courses.
- Any future coding-exercise bank-owned private table must be added to the bank-to-course copy hook and the bank-activity delete cleanup hook, then manually verified by publishing a bank activity, adding it to a course, checking the course-owned plugin rows, and deleting the bank activity.
- Bank activity duplication uses `onBankActivityDuplicated` to copy private bank reference/test rows to the new activity; moves retain the bank activity ID and require no plugin-row migration. Future bank-owned tables must also be added to the duplication hook.
- Course/bank sync uses `onCourseActivityCreatedFromBankVersion` for bank-to-course replacement and `onCourseActivityPublishedToBank` for course-to-bank replacement of private reference/test rows. Core owns immutable version creation and permissions. Any attempt permanently locks bank-to-course retrieval, while course-to-bank publication remains allowed because it changes only bank authoring and the course copy's provenance link.
- Core bank-version comparison includes public coding-exercise config only. Private reference/template/test rows are current bank state rather than immutable per-version snapshots and must not be presented as historical diffs.
- Generic coding-exercise bank versions are created only for changed Published saves. Draft saves update mutable generic and private bank authoring without creating a version; private data still lacks per-version snapshots.
- Enabled hidden tests must validate against the private reference solution before they are saved.
- Graded submissions are handled separately from sample runs through `coding-exercises/submit`.
- Teacher authoring separates student-facing starter code from a private reference solution; the reference solution must never be stored in public activity config.
- Standalone gradebook **Review all** may load that reference solution and latest submission test results only through teacher-authorized private routes; it pairs the solution with one hoverable pass/fail bar per enabled hidden test and never exposes private solution data to students.
- Coding exercises use a single template-based authoring model; older `program` and `function` configs should be normalized forward rather than preserved as separate modes.
- Non-student-visible composition pieces such as the hidden template scaffold are stored in plugin-owned private data and assembled server-side before Judge0 execution.
- Template-mode authoring uses a single hidden scaffold editor with a `{{ STUDENT_CODE }}` insertion marker and optional `{{ TEST_CODE }}` hook; older prefix/suffix data should remain readable for backward compatibility.
- Template-mode teachers mark student-visible scaffold lines directly in the editor gutter; non-visible blocks collapse into a single language-appropriate hidden-code placeholder in the student-safe scaffold.
- The browser-facing `Activity.config` carries only the student-safe projected template scaffold, never the full hidden template source.
- Both visible sample tests and hidden tests can provide language-specific harness code that should be injected at `{{ TEST_CODE }}` when present so template-based exercises work across Python, C, C++, JavaScript, and similar runtimes.
- Teacher test authoring uses collapsible sample-test and hidden-test cards with saved validation status and per-test failure details.
- The same coding-exercise activity UI should work in both course-scoped teacher pages and group-scoped student assigned-activity pages by swapping the API client boundary rather than forking the plugin UI.
- The learner workspace is a responsive editor-left/test-runner-right layout with a two-thirds/one-third default split and an accessible pointer/keyboard-resizable divider; it collapses to one column at narrow viewport widths. Its full-screen focus mode elevates the same mounted workspace into a fixed viewport overlay, preserving editor state, selected test, output, and divider position; students leave it with the exit control or Escape, and a completed submission exits it before showing confirmation. In the desktop grid, the editor and test runner occupy the same row and stretch to the same height, with the submission action in a separate row below the editor. Its custom test selector is built on the shared anchored-popover primitive, lets the selected label wrap, and expands the option menu outside a narrow runner column so full test names remain readable. The selector lists every visible test plus a separate `Personalized test`; presets display input, expected output, comparison mode, and ordering as compact read-only information while saved harness code remains hidden and is applied automatically. Personalized input is retained separately and remains editable, expected-output information is hidden, the run sends no harness and explicitly disables output comparison, and the UI presents raw execution output without a pass/fail mark. Runner controls remain top-aligned and only the output panel grows into unused vertical space.
- Preset-test and submission outcomes use an accessible green checkmark or red cross instead of exposing paired Cognelo/Judge0 status labels such as `completed · Accepted`; pending records retain a neutral pending label, personalized runs have no outcome mark because they make no output assertion, and failure diagnostics remain visible below the outcome.
- Blank or whitespace-only learner source is not executable: the learner Run and Submit actions remain disabled, and server schemas reject direct empty payloads before Judge0 runtime lookup or execution persistence.
- Group-scoped student coding-exercise access uses assigned-activity routes under `groups/:groupId/activities/assigned/:activityId/...` to avoid route conflicts with teacher assignment-management endpoints.
- Coding plugin routes must remain plugin-owned and mounted through generic course/group plugin dispatchers, not hardcoded as plugin-specific API route files in `apps/api`.
- Student coding uses the shared Monaco editor from `@cognelo/activity-ui`, while teacher authoring still uses the in-house editor for the lighter authoring workflow. Monaco's pinned browser distribution is served from Cognelo's first-party web assets rather than the loader's runtime CDN so restricted SEB sessions can initialize it; the shared controlled-textarea fallback must preserve source and template prefix/suffix boundaries if initialization still fails.
- The student-facing prompt is Markdown stored in public coding-exercise config. Teachers author it with the shared `RichTextEditor`; its Visual and Markdown bodies have one fixed shared height, scroll internally, resize together from the accessible bottom handle, and each support the far-right full-screen action. The toolbar equation action and rendered KaTeX widgets open the shared mouse/touch equation builder for inline/display insertion, editing, and removal while round-tripping original delimited source. Complete delimited formulas entered or pasted as Visual text are preserved without escaping and render after focus leaves. Its table action and contextual cell controls create and reshape portable GFM tables; the first row remains the header, and cell merging is intentionally omitted because GFM cannot represent spans. Its image action uses the core reference-managed media service, requires alternative text, supports pixel/original-percentage/container-percentage width, and supports later replacement/edit/resize/removal by clicking the rendered image. Learner current-attempt views render the prompt with the sanitized shared `MarkdownRenderer`, including images, tables, KaTeX-compatible inline math, and `$$ ... $$` display math, while previous-submission views continue to omit it.
- Standalone student source code loads and autosaves through core `ActivityResponseDraft`; serialized saves prevent stale requests from winning, activity-object identity refreshes do not reset the editor, and every completed or failed submission clears the draft. Test-embedded coding exercises remain on the Test execution host and `TestItemAttempt` autosave path. Each Test item workspace is remounted on navigation and derives its initial source directly from that activity's config: saved source wins when present, otherwise the configured starter code is shown and saved. Monaco hidden-template prefixes/suffixes are display-only and read-only/loading change notifications must never enter student state.
- Standalone coding exercises participate in the host's New attempt/Previous submissions tabs. Execution history is projected into attempts without a schema field: chronologically ordered runs accumulate until the next submission, that submission closes the group, and runs after the newest submission belong only to the current attempt. Previous submissions are newest-first accordions showing the submitted source, submission outcome, and every grouped run, including each run's saved stdin. A completed or failed submission resets the editor to starter code, clears current-run UI and the response draft, moves the attempt to history, and opens a result confirmation. Summative group submissions also create, submit, and grade a shared core `ActivityAttempt`; history and submit responses expose attempt availability, including legacy plugin submissions, so exhausted assignments reopen with only Previous submissions and confirmation returns the learner to course content.
- Plugin-owned user-facing translations should live inside the plugin package rather than in the host app's global i18n file.
- Teacher authoring forms must register with the shared unsaved-change guard from `@cognelo/activity-ui`; future coding-exercise tabs/settings should keep `isDirty`, save, and discard behavior wired through `useUnsavedChangesGuard`.
- The teacher authoring form exposes that same combined public/private draft through the shared responsive `EditActionBar`; its status becomes saved only after the entire multi-part save succeeds.
- AI-assisted coding-exercise authoring uses the selected question-authoring AI agent. Prompt generation fills only the student-facing prompt from description/language/subject context.
- Every coding generation stage receives the shared knowledge mode and complete subject catalog as a curriculum boundary. Selected skills additionally constrain output; suggestion maps the generated prompt/solution/tests to exact subject skills and updates only the unsaved host draft; ignore neither reads nor changes that draft and performs no mapping pass.
- AI-assisted coding-exercise solution/test generation is staged. Solution generation fills the teacher reference solution and a constrained execution template, clears starter code, and does not create tests. Test generation then uses the student-facing prompt, reviewed reference solution, and template to create visible sample tests and hidden tests after server-side validation against Judge0.
- AI-generated coding-exercise templates should use only two portable shapes: `{{ STUDENT_CODE }}` for full-program stdin/stdout exercises, or `{{ STUDENT_CODE }}\n\n{{ TEST_CODE }}` for callable-unit exercises with per-test harness code. Do not generate body-insertion templates for AI assets.
- AI-generated hidden tests are capped at 15 so teachers can review them comfortably.
- Full-program AI tests must not target inputs that make the reviewed reference solution return a non-zero exit status, because Judge0 treats that execution as failed even when stdout matches. Floating-point boundary cases must use values safely inside/outside the threshold unless language-level representation has been accounted for. Test correction prompts explicitly repeat both constraints.
- Visible and hidden tests support `exact`, `contains_lines`, and `regex` output modes. Missing mode data always normalizes to `exact` for backward compatibility. Exact remains Judge0-backed. Contains-lines requires every non-empty expected line to occur as literal text within a stdout line, allows surrounding text, ignores trailing whitespace on both expected and actual lines, preserves leading whitespace, requires duplicate expected lines to have the same number of non-overlapping output occurrences, and can optionally enforce occurrence order. Regex uses `re2-wasm`, searches stdout, rejects empty/invalid patterns and patterns longer than 4,000 characters, and deliberately does not support backreferences or lookaround. Non-exact modes omit Judge0 `expected_output`, require Judge0 Accepted first, and then use the shared Cognelo comparator across reference validation, sample runs, and hidden submissions.
- AI test generation treats uniform Judge0 compilation failures and uniform internal sandbox failures as fatal reference/runtime errors rather than asking the model to rewrite otherwise valid test JSON. Local Apple Silicon development uses the pinned ARM64/cgroup-v2 image documented above; production continues to use the documented Ubuntu sandbox host.
- Judge0 status 13 is an infrastructure failure, not evidence about learner correctness. The shared Judge0 client must throw a retryable `JUDGE0_INTERNAL_ERROR` before output comparison so runs, hidden-test submissions, and reference validation never turn an internal sandbox failure into a failed test or partial grade. Operationally failed `submit` executions are retained for diagnosis but omitted from learner attempt history/counting and teacher review; detection covers the current `failed-before-result` phase plus legacy records with top-level or per-test Judge0 status 13. Preceding practice runs remain current for the retry, and AI evaluation refuses these executions. If an older bug already created a core summative attempt, use the audited core submission-delete workflow rather than mutating or deleting it inside the plugin. Keep the token and decoded diagnostic in server logs for operations, while returning only a safe service message to the browser.
- AI-generated coding-exercise prompts should be concrete scenario-based tasks rather than meta/concept-only prompts. For example, teach pointer/reference concepts through a small realistic use case instead of asking students to "illustrate pass-by-reference".
- Programming Exercises declare `supportsAiFeedback` and `supportsAiFeedbackGrading`. Private `aiFeedback` configuration lives inside the reference-solution row and is valid when disabled or, when enabled, only with rubric name/version, evaluator instructions, unique criteria totaling 100%, and deterministic/AI grading weights totaling 100%. The existing bank/course private-data lifecycle copies this configuration.
- The rubric authoring UI derives inline validation from the same plugin schema before Save. Criterion add/remove operations allocate collision-free stable IDs and rebalance integer criterion weights to exactly 100%, eliminating the former zero-weight and remove-then-add duplicate-ID drafts that surfaced only as generic API validation failures.
- Each submitted `PluginCodingExerciseExecution` stores `aiFeedbackConfigSnapshot` before any later teacher evaluation. Evaluators prefer this immutable submission-time private snapshot over current authoring state; legacy executions without a snapshot may fall back to current private config.
- Formative submission invokes AI feedback directly when the course gate and activity configuration are effective. Summative submission never invokes or enqueues AI; it leaves AI-graded attempts submitted until a teacher calls the shared gradebook endpoint. The plugin evaluation handler also supports Compound Test child attempts through the child's plugin execution reference.
- `PluginCodingExerciseAiEvaluation` is append/version oriented and private. It retains rubric/request snapshots, raw response, parsed/sanitized feedback, provider/model, prompt/schema/rubric versions, hashes, latency, deterministic/AI/combined scores, weights, and failure text. Student responses expose only sanitized feedback.
- AI grading composes the deterministic test percentage and rubric percentage using the activity's snapshotted weights and returns a normal core grading result. Feedback-only mode leaves deterministic grading authoritative. Only feedback that contributed to the grade is marked challengeable by core.
- Programming Exercises register `aiFeedback.rendererKey` plus `aiFeedback.teacherReview` submission, empty-draft, and revision handlers. Detailed gradebook **Feedback** is enabled for every submitted exercise and whole-class navigation includes all submitted learners. Manual and generated feedback share one multiline field each for Summary, Strengths, and Improvements; blank narratives are valid and omitted from learner views. Generated rubric criteria expose editable percentages and narrative. Score changes preserve deterministic results plus configured weights, recompute AI/combined scores, return a plugin grading result, and run through the core audited regrade path with `feedback_teacher_grade_adjusted`; narrative-only changes do not regrade. Core retains pre-grade manual feedback on the attempt, carries it into later grading, records `feedback_teacher_authored`/`feedback_teacher_revised`, keeps `PluginCodingExerciseAiEvaluation` immutable, permits generated-feedback revisions until that version is challenged, and uses mechanism-neutral learner copy.
- The root Prisma seed owns an idempotent teacher-feedback test cohort for `seed-activity-c-median-feedback`. The corresponding published bank/course C median exercise has five hidden tests and a 60% deterministic/40% rubric snapshot, is assigned summatively to every Programming 101 section, and seeds one submitted execution/core attempt for every linked Section A/B learner. A clean seed has 36 submissions (six correct, three compile failures, and varied logic/output failures). It deliberately creates neither `PluginCodingExerciseAiEvaluation` nor core `Grade` rows so the dataset begins at the authentic teacher-triggered summative-review boundary; pre-existing linked learners in those sections are included rather than silently left without work.
