# Coding Homework Grader memory

- The [approved workflow](../../../docs/CODING_HOMEWORK_SUBMISSION_WORKFLOW.md) is authoritative. Each student hands in individually; preparation manages uploads only, never browser code edits. A ZIP replaces the entire draft collection and retains its internal folders. Individual-file UI uploads use the root; destination-folder and folder-creation controls are intentionally absent.
- Drafts create no academic attempt. Revision checks and a per-student workflow lock serialize edits and final hand-in. Freeze copied, hash-verified files and enqueue generation in one transaction. Only teacher cancellation/deletion permits another hand-in.
- Private teacher solutions belong to course/bank authoring owners. Copy/sync hooks include them but clear operational enablement, reference selection and both explicit model choices. Never expose their source through student projections or add it automatically to course embeddings.
- Teacher solution edits use owner locks and revision checks, ignore macOS ZIP metadata, and validate source text before JSON persistence. ZIP replaces the catalog; single-file replacement refreshes only that file’s functions. Removing a function excludes it from the catalog without changing its source file. Prune linked saved requirements atomically and reconcile the editor’s saved baseline while preserving unrelated draft edits. Reject changes while submissions are enabled.
- Validate C signatures without execution: name, argument types/count and return type; ignore parameter names/storage qualifiers and equivalent array parameters. Keep typedef spelling, pointer depth and pointee qualifiers. Academic gaps/syntax incompleteness require acknowledgement; archive, storage and analysis-resource limits block.
- Material plugins own extraction and index preparation/refresh services. Call them through core only. Homework owns selection and pinned snapshot IDs, never its own material vector store. Question-model changes do not invalidate embeddings. Repository freshness is checked at enablement, not per student.
- Course authoring uses host Reference materials and Settings portals. Selection and embedding model stay in Reference materials; question-generation model, concurrency, embedding generation and final-submission opening stay in Settings. Keep one mounted workflow state across tabs and assignment saves. Incidental settings refreshes must preserve unsaved selection; progress dialogs render outside hidden panels. Bank authoring has no course-reference/settings tabs.
- Explicit model choices go through core access checks. Freeze the question model at hand-in and embedding model with the reference snapshot; never include tokens. Existing jobs keep their model when the teacher changes the next-submission choice. Legacy generation and required-function selection also honor explicit homework generation overrides; all supported text providers are permitted. See [AI connections](../../../docs/AI_MODEL_CONNECTIONS.md).
- Material selection, embedding model and static requirements are locked while final submissions are enabled. Generate a new prepared selection after selection changes, reusing unchanged compatible vectors. Existing frozen submissions retain their snapshot and generation settings.
- The durable queue defaults to 2, caps the entire homework queue at 4, and supports teacher changes for waiting jobs. Heartbeats/retries recover interruption; complete questions publish atomically under the workflow lock after verifying job ownership. Cancelled requests retain provider slots until the worker unwinds. Legacy analysis/generation entry points must not mutate version-2 submissions.
- `assessmentFlow: deferred` separates preparation from SEB/timing. Answer routes stay guarded; the verified Answer action creates/resumes the core attempt. Never disclose ready questions through the preparation projection. Preserve existing starts for historical/continued attempts.
- Saves and completion lock the plugin submission and core attempt. After the authoritative deadline, discard incoming answer content and submit saved answers including blanks. Durable deadline jobs and the generic timed-finalization hook use the same path and recheck effective exceptions.
- Teacher cancellation retains old files/questions/answers and audit evidence, withdraws its associated grade, grants one replacement after released grades, and invalidates queued/running work. Keep grade-release state for the rest of the class. Details-page management includes work still queued without core attempts.
- Course managers author/open submissions. Grading and cancellation use scoped course/section staff capabilities. Student APIs expose safe states/counts and generic failures, never private diagnostics, model prompts, retrieval provenance, raw model output or stored names.
- Generated Prisma clients are ignored local build artifacts. Do not recommit them: they embed machine paths and native binaries. Keep schemas/manifest migrations tracked and run normal database generation commands.
- Student view is inspection-only; never create and delete academic submissions to emulate preview. Submitted-work exports and historical review use retained files and questions without regenerating or executing them.
- Use shared Markdown, action icons, dialogs, application timezone and content-closure contracts. Autosaves preserve answers across reloads. Preparation/material actions are cancellable; student background question generation deliberately has no Cancel action.

See [reference](docs/REFERENCE.md) for routes/persistence and [historical decisions](docs/DECISIONS.md) for the retained legacy pipeline. Track current work in the [progress record](../../../docs/CODING_HOMEWORK_IMPLEMENTATION_PROGRESS.md).

- Workflow errors must go through `useNotifications` as well as the inline state, including save/model/refresh and reference preparation failures. Name the failing material and mark its row; retain successful indexes for retry. Cancellation is not an error notification. Keep the operation owned until the post-action refresh settles, and never overwrite unsaved model choices after a failed/cancelled action. ZIP extraction belongs to the file material plugin through core.

- At hand-in, resolve and freeze the course Subject’s teaching language in `questionLanguage`; never let the submitted/session `locale` choose question language. Older queued work resolves it from the course. Promote private generation instructions to the system prompt in both prepared and legacy generation, with the fixed language/JSON/privacy contract intact. Settings exposes the existing `generationInstructions` field through the same activity draft/save guard.
- Question context is an allowlisted snapshot of submitted code, filename, function name, language and truncation status. Existing questions may resolve their retained function/file only when both belong to the question’s submission. Cap excerpts at 24,000 characters (the model evidence bound), retain the full read-only file viewer, and never project ASTs, storage paths, teacher prompts or retrieval examples. Questions/context remain behind the Answer/SEB gate.

- Portaled generation-instruction controls share the activity saved baseline and stay hidden until authoring data loads. Capture the textarea value before scheduling a functional state update; reading the event target inside the updater can lose portaled edits. Render authoring progress in the document body so Settings saves remain visibly blocking when Activity is hidden.

- Prepared and submitted files use shared `SideNavigation`/settings layout, not a plugin-specific tab style. Open the first file automatically; preserve selection through workspace polling and reset it for a new submission. Keep code read-only and horizontally contained, including on mobile. Abort and ignore stale reads on tab changes/unmount, clear old content immediately, and give failures a retry plus notification. Filenames appear only in the left tabs; no repeated heading or file size above the aligned content pane. Draft revisions trigger a fresh selected-file read, including same-path replacements. Tab delete crosses are sibling buttons, never nested interactive controls, and require confirmation; they disappear after hand-in.

- Snapshot native FileList entries before awaiting replacement confirmation; clearing the file input mutates its live FileList. Keep File objects in the operation so confirmed same-path/ZIP replacements upload the chosen bytes.

- Student checks are explicit UI actions backed by fresh preparation validation. Do not reveal the requirements list before Check my submission. Gate Submit on the checked current revision/result and, for academic gaps, a fresh incomplete-work acknowledgement; invalidate both after changes. Explain structural-only scope and confirm immutability before hand-in. Server-side validation at hand-in remains authoritative.
- Student resources are two conditional downloads, never a raw attachment list. Provided-file ZIPs must select only the authorized owner’s `provided_file` attachments, exclude private solutions/requirements/PDF statement data, stream bounded chunks, validate file sizes/hashes, and preserve all duplicates under safe unique names. A sole provided ZIP passes through unchanged. Keep `activity-file` PDF previews inline unless `download=1` explicitly requests attachment disposition.

- Bulk draft removal is one revision-checked metadata transaction under the existing workflow lock. Clear files and folders together, reject frozen/stale submissions, then remove only the obsolete draft bytes after commit. Both per-file and bulk cancellation preserve the previous structural check; confirmed changes invalidate it.

- Challenge difficulty tests understanding, not obscure knowledge or endurance. Target one code-grounded point with a complete answer in 2–3 sentences, reasonable for the student who wrote it at this course level. Vary concrete valid/boundary inputs, conditions/guards and other local choices; avoid long traces, unrelated subquestions, missing context, traps, or treating buggy/undefined behavior as a correct deterministic result. Teacher focus instructions remain authoritative within this short, fair scope. Both generators receive previous questions for diversity. This is generation guidance, not a sentence-count restriction on saved student answers.
