# Coding Homework Grader Plugin Memory

This file is for coding-homework-grader-specific memory only.

## Current Decisions

- Assignment PDFs and teacher-provided files are plugin-owned activity attachments, not separate course content resources. The secure `coding-homework-grader/activity-file` route serves them after activity/course/bank authorization; PDFs use inline disposition for teacher/student viewing, while other files download normally.
- `provided_file` attachment rows belong to bank or course activities and are copied by the bank-to-course hook. Teacher authoring can upload/remove/open them, and assigned students receive sanitized attachment metadata plus authorized open links.
- Challenge reference extraction combines prior visible course content with activity-owned sources: assignment Markdown, locally extracted assignment PDF text, and extractable provided files. Provided C files are parsed into function-level AST reference documents. Analysis merges activity-document similarity matches with content-plugin search matches, retaining source provenance in nearest-example audit data.
- The plugin now supports the first complete manual-grading loop. Temporary ZIP preflight, final ZIP submission, submitted-function candidate analysis, challenge question generation, student challenge answer submission, core gradebook attempt submission, and teacher manual grading review are implemented.
- Phase 3 added the first teacher authoring surface in `src/web/coding-homework-grader-activity-view.tsx`; it registers with the shared unsaved-change guard and is wired into both course activity pages and activity bank authoring pages.
- Future settings, submission, or review forms should also register with `useUnsavedChangesGuard`.
- Phase 2 added plugin-owned Prisma schema, generated client, database manifest, and activation migration coverage for assignment, bank assignment, requirement set, bank requirement set, attachment, documentation snapshot, reference function, submission, submission file, submission function, challenge question, and review tables.
- Phase 3 added the bank-to-course copy hook for assignment prompt/settings, requirement sets, and safe attachment records. Course-owned copies must remain independent from later bank edits.
- Phase 4 added `src/documentation.ts`, course-only documentation preview/snapshot routes, and the teacher UI section for prior course documentation. It resolves the visible content-tree anchor for the activity and includes only visible content rows before that anchor.
- Documentation snapshots store anchor metadata, included resource metadata, resource fingerprints, a tree fingerprint, extracted generic content documents, and activity-owned reference documents in `PluginCodingHomeworkDocumentationSnapshot.metadata`. Provided C files are parsed into function-level references during extraction.
- Phase 5 added `src/extraction.ts` and the course-only `coding-homework-grader/documentation-extraction` route. It stores extracted generic documents and diagnostics in `PluginCodingHomeworkDocumentationSnapshot.metadata.extraction`.
- The Coding Homework Grader must not branch on concrete content type keys or import content type plugins for extraction. It must call core's generic `getContentResourceEmbeddingDocuments` dispatcher, and each content type plugin owns its own text/PDF/repository extraction behavior.
- Legacy material snapshot entries are diagnosed as unavailable in the extractor rather than parsed in this plugin. New extraction support should be added by migrating behavior into content type plugins or by adding a content type plugin wrapper.
- Phase 6 added `src/parsers.ts` with `createCodingHomeworkParserRegistry`, `parseCodingHomeworkSourceFiles`, and `codingHomeworkCParserAdapter`.
- The C adapter is intentionally conservative and dependency-free for the first implementation. It extracts top-level C function definitions, masks comments/strings for deterministic serialization, emits normalized `c-ast-v1` text, and returns recoverable diagnostics. A future Tree-sitter/compiler-backed adapter can replace internals while preserving the exported parser contract.
- Future language support should add new parser adapters to the registry rather than branching in submission, validation, embedding, or question-generation workflows.
- Phase 7 added `src/zip.ts`, `src/validation.ts`, and `src/preflight.ts`. The ZIP reader is dependency-free, reads central-directory entries for stored/deflated files, and reports diagnostics for unsafe paths, encrypted entries, unsupported compression, truncated data, and size mismatches.
- Structure validation is the shared gate for both preflight and final submissions. It applies the teacher requirement set, honors ignored paths, validates allowed extensions, checks required files/folders/functions, calls the parser registry for source functions, and returns separate buckets for missing required items, parser diagnostics, unexpected/unsupported items, ignored files, valid files, and valid functions.
- Preflight uploads create `PluginCodingHomeworkSubmission` rows with `kind = preflight` and `status = structure_valid` or `invalid_structure`, plus temporary `submission_zip` attachment metadata under `storage/coding-homework-grader/preflight`. They must not create core gradebook attempts, challenge questions, or final submission file/function rows.
- Phase 9 added `src/submission.ts`, `coding-homework-grader/assignment`, and `coding-homework-grader/submission`. Assigned students can load the prompt, submit a final ZIP, get the same structure validation summary as preflight, and see latest submission status.
- Final submissions reuse the same ZIP reader and validation service. Valid final submissions create durable `PluginCodingHomeworkSubmission` rows with `kind = final`, a non-temporary `submission_zip` attachment, extracted files under `storage/coding-homework-grader/submissions`, and `PluginCodingHomeworkSubmissionFile` rows. Invalid structure submissions record `status = invalid_structure` and the validation summary but do not write the ZIP or extracted files.
- Final ZIP submission creates durable plugin artifacts and enqueues analysis and challenge generation, but it does not create a core gradebook attempt immediately. For summative assignments, the core attempt is created and submitted only after the student finalizes all challenge answers.
- Phase 10 added `src/analysis.ts` and the `coding-homework-grader/submission-analysis` route. Valid final submissions now automatically analyze submitted source files, parse functions, store deterministic dev embeddings, retrieve nearest prior examples through core/content-plugin vector dispatch, compute divergence scores, and mark selected candidates in `PluginCodingHomeworkSubmissionFunction`.
- Submitted function embeddings and candidate metadata are plugin-owned assessment artifacts. Prior course-content similarity must continue to go through `searchContentResourceEmbeddingDocuments`; do not add content-type-specific reference extraction or vector-table reads to this plugin.
- Candidate analysis stores audit metadata under `PluginCodingHomeworkSubmission.metadata.analysis` and leaves the submission status at `structure_valid` until challenge generation moves it to `challenge_ready`.
- Phase 11 added `src/generation.ts` and `coding-homework-grader/challenge-generation`. This route is teacher-only for assigned group activity contexts and can trigger or retry generation for analyzed submissions.
- Challenge generation uses the teacher's configured question-authoring AI agent connection through server-side core services. It should never expose provider keys, AI prompts, nearest examples, or other course-material provenance to students.
- Generated challenge questions are stored in `PluginCodingHomeworkChallengeQuestion` with prompt version `coding-homework-grader.challenge-question.v1`, generation model, selected function ID, nearest examples, prompt hash/text, raw model response, attempt count, function name, and divergence score for future teacher audit UI.
- Successful challenge generation replaces the stored question set for that submission and moves the submission to `challenge_ready`. Failed generation marks the submission `failed` with `processingError`; a later teacher retry can run again if selected candidate functions still exist.
- Phase 12 added automatic student-path challenge generation after valid ZIP submission. The student submission route now validates the ZIP, analyzes submitted functions, generates questions, returns a sanitized question payload, and leaves the submission at `challenge_ready` until final answers are submitted.
- Automatic student-path generation uses a course teacher/owner's configured non-local question-authoring AI connection through core. Students do not need personal AI preferences, provider keys stay server-side, and local Ollama connections are rejected for Coding Homework Grader challenge generation.
- Student-facing challenge question payloads must stay sanitized: expose question ID/order/text plus student answer state only. Do not expose `nearestExamples`, generation metadata, prompt text, raw model output, generation model, or source/reference provenance to students.
- Phase 12 added `src/challenge-answers.ts` and `coding-homework-grader/challenge-answers`. `PUT` saves draft answers while preserving `challenge_ready`; `POST` requires every generated question to have a non-empty answer and moves the plugin submission to `ready_for_grading`.
- Once a submission reaches `challenge_ready`, the student UI locks the ZIP upload for that attempt. Once it reaches `ready_for_grading`, challenge answers are read-only.
- Phase 13 adds core gradebook integration. For summative assigned activities, final answer submission creates and submits a core `ActivityAttempt` with `pluginKey = "coding-homework-grader"` and `pluginAttemptRef = PluginCodingHomeworkSubmission.id`, then stores that core attempt ID back on the plugin submission.
- Phase 13 adds `coding-homework-grader/gradebook-attempts`, the `coding-homework-grader-manual-grading` renderer, and web gradebook wiring. Teachers review submissions from the activity gradebook detail page via Review/Grade; the panel shows submitted file metadata, generated questions, student answers, selected function source code, and manual score/feedback fields. Saving uses the existing core gradebook override workflow, so released visibility follows normal gradebook release behavior.
- Phase 14 operational hardening added `src/processing.ts`, final-submission `idempotencyKey` support, processing timeline metadata, categorized retryable/non-retryable processing errors, and the teacher-only `coding-homework-grader/reprocess` route. Reprocessing reruns analysis and challenge generation only for unfinished/failed final submissions, and derived function/question rows are replaced rather than duplicated.
- Long-running final-submission analysis/question generation now uses the shared core background job service. The plugin registers `coding-homework-grader.process-submission`, student uploads enqueue that handler, the API starts the default in-process worker, and the student UI polls latest submission state until questions are ready or processing fails. Centralized rate limiting remains a platform-level future item.
- The root Prisma seed now includes a complete dev fixture for this plugin: `seed-activity-coding-homework-grader` / "Coding homework grader: INF-155 TP1 Labyrinthe" is a C labyrinth assignment in Programming 101, assigned to Section A with summative metadata and a gradebook item. Seeded plugin rows include bank/course assignment prompt settings, bank/course submission requirements, a deterministic PDF attachment copied from `tmp/INF155-A2023-TP1.pdf` when present, and a ready group-scoped documentation snapshot over the extracted TP1 statement and starter-file documentation built from `tmp/FichiersFournis`. Required functions include `lab_afficher_grille`, `lab_calculer_deplacements_possibles`, `lab_choisir_deplacement`, `lab_est_cases_adjacentes`, `lab_est_une_sortie`, `lab_resoudre_profondeur`, `charger_labyrinthe`, `selection_menu`, and `menu_charger_labyrinthe`; `generer_nombre_aleatoire` is optional. The seed preserves existing teacher question-authoring AI preferences and only seeds them from a non-local provider, so challenge generation is not silently routed to local Ollama.
- Phase 8 vector work should be shared platform/content-plugin infrastructure, not a plugin-local JSONB vector index. Content type plugins own extraction/chunking semantics and invalidation decisions; production vector persistence/search should move to common platform pgvector tables so activities can search all relevant course content across content types. The Coding Homework Grader asks core/content-plugin dispatchers for similarity over prior snapshot resources and stores only assessment/audit metadata such as selected references and nearest examples.
- Phase 8 added `src/reference-search.ts` and the `coding-homework-grader/reference-search` route. It stores `latestReferenceSearch` on `PluginCodingHomeworkDocumentationSnapshot.metadata` with query fingerprint, matches, diagnostics, and exact matched text for auditability. Do not add prior-content vector storage to this plugin.
- Pgvector migration is intentionally deferred until vector-size/model decisions are made. Pending decisions include embedding provider/model key, dimensions, multi-model table strategy, whether submitted functions share the common vector tables, index type, content fingerprint invalidation, and sync vs background indexing.
- Activity-bank authoring intentionally does not show documentation preview or snapshot actions because banks do not have a course content tree.
- Phase 1 renamed the scaffold package to `@cognelo/plugin-coding-homework-grader`, the plugin and activity keys to `coding-homework-grader`, and the plugin database namespace to `plugin_coding_homework_grader`.
- The picker display name is Coding Homework Grader and the activity remains in the Programming category.
- Phase 0 added `src/algorithm.ts` with stable TypeScript-facing contracts for source files, submission requirements, structure validation summaries, parser adapters, AST functions, embeddings, candidate selection, and challenge question generation.
- The first parser implementation should target C, but the contracts are intentionally language-neutral so future parser adapters can support additional languages.
- The research prototype in `tmp/challenge-questions/scripts` is reference material only. Production plugin code must not import, execute, or otherwise depend on files under `tmp`.
- The initial challenge question prompt version is `coding-homework-grader.challenge-question.v1`.
- Requirements are modeled as separate course and bank requirement-set tables, not only as JSON embedded in assignments, so uploaded/imported structure requirements can evolve independently from prompt authoring.
- Assignment PDF, provided-file, and requirements uploads are stored under `storage/coding-homework-grader` with attachment rows carrying safe metadata and SHA-256 hashes. The physical file is shared by copied attachment rows for now. Phase 15 will harden webserver-filesystem storage behind an adapter boundary so an external backend can be introduced later if needed.
- Teacher authoring exposes its guarded activity/configuration draft through the shared responsive `EditActionBar`. Uploads, imports, extraction, and processing operations that persist independently remain outside that bar's saved-status claim.
