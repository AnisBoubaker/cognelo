# Plugin: Coding Homework Grader

`@cognelo/plugin-coding-homework-grader` provides C homework preparation, immutable hand-in, queued challenge questions, timed/SEB answering and teacher grading, individually or in teams.

For team homework, enable **Team work** in core Activity settings and choose a grouping plus the unteamed-student policy for each section under **Group assignment**. All current teammates share preparation and one frozen hand-in. Homework **Settings** chooses whether to generate separate question sets; the default is common questions with private individual answers. Timers and grades remain individual. Late joiners receive their own answering participation; moving teams starts fresh and withdraws the previous active grade. Empty-team work is erased. When individual submission is disabled, students without a team see assignment resources and a notice that they must join a team before uploading or submitting; preparation controls are hidden. See [team activity rules](../../../docs/TEAM_ACTIVITY_SUBMISSIONS.md).

Students prepare work by choosing individual files (uploaded at the root) or replacing the whole collection with a ZIP that preserves its folders. The preparation UI has no destination-folder field or Create folder action. Files persist across visits in the shared left-tab explorer, with the first file opened automatically. Before **Submit my work**, a tab’s cross removes that file after confirmation, and **Remove all files** clears the draft after confirmation. File contents remain read-only. There is no browser code editor. Students explicitly choose **Check my submission** to see a structural result. Valid structure reveals Submit my work; academic gaps require **I want to submit incomplete work** before showing it. File changes clear the check/acknowledgement. The UI explains that required filenames/function signatures do not prove correctness, and submission requires an immutable-work warning. File safety failures remain blocking. A prominent **Your work has not been submitted** notice follows verification and points to **Submit my work**.

Teachers upload a private C solution and choose required filenames/functions manually or with AI assistance. ZIPs replace the solution; files and detected functions can be removed individually or cleared together, with linked requirements reconciled. In a course, **Reference materials** holds the embedding connection/model and material selection (defaulting to visible materials before the activity). **Settings** holds the question-generation connection/model, private AI question-generation instructions, generation concurrency, Generate embeddings, the manual final-submission switch, and an optional **Submission deadline** in the course timezone. Late work may be disallowed, unlimited, or limited to a days/hours/minutes period after the deadline. Accepted late hand-ins show how late they were to students and teachers, including Review and grade. Both tabs preserve the activity draft and reference selection. Preparation shows the current material; failures name it inline and in the shared notification center, and retry reuses completed indexes. Material plugins own extraction/index refresh through core. GitHub freshness is configured on each repository material and checked when submissions open.

At a finite deadline or bounded late cutoff, saved files not yet handed in are submitted automatically when the student opens the page or staff opens Class overview. Academic gaps are acknowledged automatically; empty drafts and unsafe/unreadable files are not silently submitted. Unlimited late work and homework without a deadline remain manual. Automatic recovery uses the cutoff for lateness and does not start answering.

Final hand-in freezes the actual validated files and atomically queues generation. Default parallelism is 2 students, configurable up to a server-wide ceiling of 4. The generation panel shows a spinner and live queue position while waiting, then switches to an active generation message without suggesting that the student leave. **Answer challenge questions** starts the core attempt and timer after any required SEB verification. Each challenge displays its submitted function code and filename read-only beside the answer area. Ordinary course materials and the complete submitted files stay accessible. Submitted work uses the shared left-tab view: filenames on the left, read-only code on the right, and the first file opened automatically. The content starts level with the first tab, without repeating the filename or file size above it. New questions use the course Subject’s teaching language, independently of the session UI language; teacher generation instructions guide question focus and style. Challenges test understanding of the submitted code through one focused point answerable in 2–3 sentences, at a difficulty a student who wrote the code can reasonably handle. Concrete cases, conditions and local implementation choices provide varied question types. Deadline finalization submits saved answers, including blanks.

Teachers can cancel queued, answering or completed submissions from the activity details page (or editor): the old work is retained, associated grades are withdrawn, late generation cannot revive it, and the student may submit again. For a team, cancellation affects every current member. **Reset this student’s challenges** retains the shared files and resets only that student’s answers, timer and grade. Team assignment and question-sharing settings lock while active hand-ins exist. Students cannot cancel their frozen hand-in or question-generation job.

Questions exclude unchanged functions from teacher-provided C/H files and ZIP contents as targets. They may still ask how the student's own function calls a provided helper or uses its result. Comments and formatting are ignored; changed implementation tokens remain eligible. Hand-in saves only a compact comparison manifest of hashes and function names, never another copy of the provided files. Private teacher solutions do not participate. See [provided-code comparison](docs/REFERENCE.md#excluding-unchanged-provided-code) for versioning and the no-eligible-code outcome.

Assignment resources appear as two conditional download actions: the assignment PDF and one ZIP containing the provided files. A sole uploaded ZIP is returned unchanged; other provided attachments are bundled with safe unique names. Teacher PDF previews/View PDF remain inline. Authorized file responses preserve bytes and content type. After hand-in, **Download submitted work (ZIP)** and read-only **Check my submission** are available for both individual and team work.

Challenge answering uses distinct numbered cards with the question first, a framed read-only code panel and a labelled answer area. Code and answer sit side by side when space permits and stack on small screens; long code scrolls within its panel. Autosave and submission behavior are preserved.

Students may submit some or all challenge answers blank. Manual submission first confirms that answers cannot be changed and lists unanswered question numbers; Cancel returns to editing. Timeouts finalize saved answers automatically without confirmation. Student operation failures use the shared notifications/history instead of a page-top error banner.

Teacher **Review and grade** uses the shared wide dialog, with an aligned toolbar and separate Questions and answers / Submitted files tabs. Submitted files use the same read-only left-tab viewer and load on demand for the selected learner/submission. Numbered question cards show the submitted code and answer, including an explicit unanswered state. Grade and feedback stay beside the content on wide screens; historical/formative review remains read-only.

**Preview indexed text** in Reference materials lets teachers inspect the saved passages used for question generation. Prepared homework shows its pinned reference version; unprepared material shows its latest saved index. The preview is read-only, paginated, private to course managers and makes no AI calls. Check that the expected teaching content is present; extraction does not guarantee completeness for every website.

## Boundaries

Private solutions, model prompts, retrieved reference excerpts, credentials, filesystem paths and processing diagnostics stay server-side. Learners receive explicit public projections. Requirements use bounded static C normalization without compilation or execution; typedef spellings remain significant. Generated Prisma clients are ignored local artifacts; track schemas/migrations and regenerate through the normal database commands.

Duplicating within a course retains independent authoring, attachments, private solutions, model choices and the same reference-material selection and prepared indexes. The copy owns a separate reference snapshot while reusing the immutable indexes, so deleting the original does not break it. Final submissions start disabled; course assignments/delivery policy and student work are not copied. Bank transfers still reset course-specific references and model choices. See [duplication](docs/REFERENCE.md#duplication-within-a-course). Student view remains inspection-only. Teacher review/grading respects course and section staff capabilities; authoring and submission opening require course management. The activity does not advertise a released student-solution capability.

Local acceptance tests use a controlled AI endpoint owned by a disposable account and scoped to its synthetic course, with real APIs, persistence, queues and browser UI. Shared login AI preferences stay untouched; see [fixture isolation](../../../tests/e2e/README.md#ai-fixture-isolation). Native SEB launch is simulated at its boundary; real activation/proof/configuration scoping is tested. See the progress record for actual checks and outstanding work.
