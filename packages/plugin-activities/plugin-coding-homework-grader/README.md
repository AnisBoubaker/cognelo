# Plugin: Programming Homework

`@cognelo/plugin-coding-homework-grader` provides C homework preparation, immutable hand-in, queued challenge questions, timed/SEB answering and teacher grading, individually or in teams.

Teacher editing guidance uses shared [contextual help](../../../docs/CONTEXTUAL_HELP.md): a circled question mark after the associated title or label, on the same row, with hover, keyboard and touch access.

For team homework, enable **Team work** in core Activity settings and choose a grouping plus the unteamed-student policy for each section under **Group assignment**. All current teammates share preparation and one frozen hand-in. Homework **Question Generation** chooses whether to generate separate question sets; the default is common questions with private individual answers. Timers and grades remain individual. Late joiners receive their own answering participation; moving teams starts fresh and withdraws the previous active grade. Empty-team work is erased. When individual submission is disabled, students without a team see assignment resources and a notice that they must join a team before uploading or submitting; preparation controls are hidden. See [team activity rules](../../../docs/TEAM_ACTIVITY_SUBMISSIONS.md).

Students prepare work by choosing individual files (uploaded at the root) or replacing the whole collection with a ZIP that preserves its folders. The preparation UI has no destination-folder field or Create folder action. Files persist across visits in the shared left-tab explorer, with the first file opened automatically. Before **Submit my work**, a tab’s cross removes that file after confirmation, and **Remove all files** clears the draft after confirmation. File contents remain read-only. There is no browser code editor. Students explicitly choose **Check my submission** to see a structural result. Valid structure reveals Submit my work; academic gaps require **I want to submit incomplete work** before showing it. File changes clear the check/acknowledgement. The UI explains that required filenames/function signatures do not prove correctness, and submission requires an immutable-work warning. File safety failures remain blocking. A yellow **Your work has not been submitted** warning follows verification and points to **Submit my work**.

Teachers upload a private C solution and choose required filenames/functions manually or with AI assistance. ZIPs replace the solution; files and detected functions can be removed individually or cleared together, with linked requirements reconciled. In a course, the core-owned **Reference materials** tab provides a searchable folder tree, status badges, saved-text previews, Generate embeddings and its own Save/Cancel bar. The embedding connection/model is configured once in **Course settings → AI** and reused across activities; the panel links there. Material selection defaults to visible materials before the activity. Hidden documents and documents inside hidden folders are offered with a **Hidden from students** label and start unchecked; selecting a folder explicitly includes all descendants. Saved choices persist. Selecting hidden references permits private AI use without making them visible to students. **Activity** contains shared left tabs: Activity, Teacher solution, Submission requirements, Question Generation, Submission settings and Simulation. The basic Activity section uses the shared WYSIWYG assignment editor and a collapsed PDF preview. Question Generation holds its On/Off switch, counts, generation model/instructions, team question policy and concurrency; Submission settings holds upload limits and links to core Activity settings for stage activation and scheduling. Core Settings places availability beside the plugin-declared File submission / Questions answering deadlines and optional durations, with section/team/student overrides and course-timezone date entry. Concepts and core Reference materials remain top tabs. Student submission management stays in Class overview. Late work may be disallowed, unlimited, or limited to a days/hours/minutes period after the deadline. Accepted late hand-ins show how late they were to students and teachers, including Review and grade. Teacher solution shows filenames on the left and only the selected file’s signatures on the right, initially selecting the first file. Submission requirements holds manual file/folder/function rules, ignored paths, allowed extensions and requirements import. One Save/Cancel bar covers the activity and all left sections, including model and concurrency. Stage scheduling belongs to the separate core assignment-settings dialog. Uploads/solution catalog changes keep their explicit persistence, and core Reference materials retains its own Save/Cancel. Navigation and incidental refreshes preserve unsaved edits. Preparation shows the current material; failures name it inline and in the shared notification center, and retry reuses completed indexes. Material plugins own extraction/index refresh through core. GitHub freshness is configured on each repository material and checked when the question stage opens.

**Simulation** checks an uploaded ZIP, shows structural issues and requires an explicit simulated submission, with incomplete-work acknowledgement when needed. It generates from that ZIP using the same generator, saved instructions, course language, references and provided-code exclusion as student work; it never falls back to the private solution. With questions off it previews file-only completion. Progress is cancellable, results are temporary and no student attempt or grade is created.

At a finite deadline or bounded late cutoff, saved files not yet handed in are submitted automatically when the student opens the page or staff opens Class overview. Academic gaps are acknowledged automatically; empty drafts and unsafe/unreadable files are not silently submitted. Unlimited late work and homework without a deadline remain manual. Automatic recovery uses the cutoff for lateness and does not start answering.

Question generation is optional, defaulting to enabled for existing homework. File-only hand-ins immediately become submitted, ungraded work for teacher review, including each team member, without AI/embeddings, challenge answering or an answering timer. Existing generation settings are retained. See [editor and optional-question policy](../../../docs/PROGRAMMING_HOMEWORK_EDITOR.md).

Final hand-in freezes the actual validated files. Core Activity settings independently activates File submission and Questions answering. Preparation is allowed before file-stage activation; final hand-in is gated. With questions inactive, frozen files wait without AI calls or an answering clock. Opening Questions answering requires prepared references/model and atomically queues eligible waiting work. Turning it off blocks new generation and answering starts; already-started answers may finish under their existing deadlines. The student sees disabled actions with Awaiting teacher activation. Default parallelism is 2 students, configurable up to a server-wide ceiling of 4. The generation panel shows a spinner and live queue position while waiting, then switches to an active generation message without suggesting that the student leave. **Answer challenge questions** starts the core attempt and timer after any required SEB verification. Each challenge displays its submitted function code and filename read-only beside the answer area. Ordinary course materials and the complete submitted files stay accessible. Submitted work uses the shared left-tab view: filenames on the left, read-only code on the right, and the first file opened automatically. The content starts level with the first tab, without repeating the filename or file size above it. New questions use the course Subject’s teaching language, independently of the session UI language; teacher generation instructions guide question focus and style. Challenges test understanding of the submitted code through one focused point answerable in 2–3 sentences, at a difficulty a student who wrote the code can reasonably handle. Concrete cases, conditions and local implementation choices provide varied question types. Deadline finalization submits saved answers, including blanks.

Teachers can cancel queued, answering or completed submissions from the activity details page (or editor): the old work is retained, associated grades are withdrawn, late generation cannot revive it, and the student may submit again. For a team, cancellation affects every current member. **Reset this student’s challenges** retains the shared files and resets only that student’s answers, timer and grade. Team assignment and question-sharing settings lock while active hand-ins exist. Students cannot cancel their frozen hand-in or question-generation job.

Questions exclude unchanged functions from teacher-provided C/H files and ZIP contents as targets. They may still ask how the student's own function calls a provided helper or uses its result. Comments and formatting are ignored; changed implementation tokens remain eligible. Hand-in saves only a compact comparison manifest of hashes and function names, never another copy of the provided files. Private teacher solutions do not participate. See [provided-code comparison](docs/REFERENCE.md#excluding-unchanged-provided-code) for versioning and the no-eligible-code outcome.

Core Activity settings configures **Require Safe Exam Browser** for Questions answering, including section/team/student overrides. File submission declares SEB unsupported so students can upload their local files in a regular browser. Unsupported file-stage SEB settings are rejected by core; question-stage SEB protects answering and saved answers. Assignment resources and read-only frozen work remain available outside SEB. A verified activity configuration covers either protected stage. Existing activity-wide SEB settings retain their previous answering-only behavior. See [stage access](../../../docs/ACTIVITY_SUBMISSION_STAGES.md#safe-exam-browser-per-stage).

Assignment resources appear as two conditional download actions: the assignment PDF and one ZIP containing the provided files. A sole uploaded ZIP is returned unchanged; other provided attachments are bundled with safe unique names. Teacher PDF previews/View PDF remain inline. Authorized file responses preserve bytes and content type. After hand-in, **Download submitted work (ZIP)** and read-only **Check my submission** are available for both individual and team work.

When editing **Files provided with the assignment**, teachers use the same left-tab file viewer as students, with the first file opened automatically. Upload multiple files to add to the collection, or one ZIP to replace it while keeping folders. Matching filenames, ZIP replacement, individual delete crosses and Remove all files use confirmations. File contents are read-only; edits save immediately and preserve unrelated unsaved activity settings. Existing file/ZIP attachments remain readable, and binary files remain downloadable. See [provided-file authoring](docs/REFERENCE.md#provided-file-authoring-collection) for limits and compatibility.

Challenge answering uses distinct numbered cards with the question first, a framed read-only code panel and a labelled answer area. Code and answer sit side by side when space permits and stack on small screens; long code scrolls within its panel. Autosave and submission behavior are preserved.

Students may submit some or all challenge answers blank. Manual submission first confirms that answers cannot be changed and lists unanswered question numbers; Cancel returns to editing. Timeouts finalize saved answers automatically without confirmation. Student operation failures use the shared notifications/history instead of a page-top error banner.

Teacher gradebook menus offer **Download submitted files (ZIP)** as soon as files are handed in, including while questions are pending. **Download all submitted files (ZIP)** follows the current section filter and includes one numbered student folder per current hand-in; team members each have a folder. Drafts, cancelled/deleted work and former team bindings are excluded. Downloads preserve folders/bytes, include no teacher-only attachments and change no attempts or grades. These actions are provided through the [shared activity contract](../../../docs/GRADEBOOK_PLUGIN_ACTIONS.md), with progress and Cancel.

Teacher **Review and grade** uses the shared wide dialog, with an aligned toolbar and separate Questions and answers / Submitted files tabs. Submitted files use the same read-only left-tab viewer and load on demand for the selected learner/submission. Numbered question cards show the submitted code and answer, including an explicit unanswered state. Grade and feedback stay beside the content on wide screens; historical/formative review remains read-only.

**Preview indexed text** in Reference materials lets teachers inspect the saved passages used for question generation. Prepared homework shows its pinned reference version; unprepared material shows its latest saved index. The preview is read-only, paginated, private to course managers and makes no AI calls. Check that the expected teaching content is present; extraction does not guarantee completeness for every website.

The display name is **Programming Homework** (French: **Devoir de programmation**). The package, plugin/activity keys, API routes and database identifiers retain `coding-homework-grader` for compatibility. Existing teacher-authored activity titles are preserved.

## Boundaries

Course authoring can save the assignment, structural requirements and explicit workflow-setting changes in one private transaction. Deadlines/late policy are now core assignment settings; legacy endpoints delegate new policy writes to core and read existing private defaults until shared scheduling is saved. Connection authorization, readiness and submission locks still apply; existing workflow endpoints remain supported.

Private solutions and processing diagnostics are teacher-only. Model prompts, retrieved reference excerpts, credentials and filesystem paths stay server-side. Learners receive explicit public projections. Requirements use bounded static C normalization without compilation or execution; typedef spellings remain significant. Generated Prisma clients are ignored local artifacts; track schemas/migrations and regenerate through the normal database commands.

Duplicating within a course retains independent authoring, attachments, private solutions, model choices and the same reference-material selection and prepared indexes. The copy owns a separate reference snapshot while reusing the immutable indexes, so deleting the original does not break it. Both core submission stages start inactive; course assignments/delivery policy and student work are not copied. Bank transfers still reset course-specific references and model choices. See [duplication](docs/REFERENCE.md#duplication-within-a-course). Student view remains inspection-only. Teacher review/grading respects course and section staff capabilities; authoring and submission opening require course management. The activity does not advertise a released student-solution capability.

Local acceptance tests use a controlled AI endpoint owned by a disposable account and scoped to its synthetic course, with real APIs, persistence, queues and browser UI. Shared login AI preferences stay untouched; see [fixture isolation](../../../tests/e2e/README.md#ai-fixture-isolation). Native SEB launch is simulated at its boundary; real activation/proof/configuration scoping is tested. See the progress record for actual checks and outstanding work.

Scheduling advertises all stage names through capabilities. File preparation starts its optional clock on the first accepted upload while its stage is active, or on activation for an existing nonempty draft; deletion/reload cannot reset it, and teacher cancellation clears it. Question time starts only on Answer, never during queue wait. Effective deadlines are the earlier stage/overall date, capped by duration; no dates means no calendar deadline. The additive plugin migration `202611090020_submission_stage_clocks` retains preparation starts and is applied with `npm run db:migrate:all`. See [stage scheduling](../../../docs/ACTIVITY_SUBMISSION_STAGES.md).
